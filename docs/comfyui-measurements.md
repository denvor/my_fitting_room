这份是**测量记录**，不是设计文档：只记"量到了什么数、口径是什么、哪些还没解释"。
README 里那些耗时数的出处、可复现方法、以及跨机器/跨版本的对照都在这份里；
规格文档看 `docs/superpowers/specs/2026-10-27-comfyui-source-design.md`；

## 0. 口径（照这六条复现，才对得上）

- **图**：线上那张 `tryon/comfy_api.build_graph`（turbo int8 + 8 步 + cfg 1 + euler/simple），不另拼图。
- **输入固定两张**：人像 `data/records/20261101-202808-ad9c/person.jpg`（`prepare_upload` 后 **1152×1536 = 1.77M**），
  衣服 `data/samples/menswear/top/denim-shirt.jpg`。指令固定 `TRYON_PROMPT`，seed 固定 **20261101**。
  **判逐位时还要固定"字节"**：同一张图走不走一遍 `prepare_upload` 会差 ±1 级（人像平均 0.94/255、最大 12），
  而这个量本身就够让成图有 0.098% 的像素通道差过 16（§24.3）—— 不核对输入字节，这种抖会被记到你改的那一处头上。
- **档位只改一个数**：`comfy_resolution()` 的返回值 —— 480p→544、720p→**864**、1K→**0**、2K→2016。
  `0` 的意思是"按参考图自身尺寸"，所以 1K 档实际喂给视觉塔的是 1.77M 像素。
- **计时**：`POST /prompt` 起，到 `/history/<id>` 里 `status.completed` 为真的墙钟，轮询粒度 0.25 秒 → 每发系统性偏大 ≤0.3 秒。
  不是服务端报的耗时，含上传后的往返。
- **一次只跑一发**，本机走 `data/generating.lock`，远程开跑前先看 `/queue` 有没有别人的活。
- **后缀只用来判时间；判逐位必须同一句话跨进程**（11-03 补，§21 就是先栽在这儿）：两发各带不同后缀，比的就不是同一张图，
  像素差 49% 也不说明任何事。反过来，"同一句话"在新起的实例里一定从头算 —— 执行缓存是进程内的，不跨重启。
  所以时间和逐位拿不到同一批数据上：要两样，就跑两批（一批各加后缀，一批一字不差）。
- **"换 seed 重跑"会命中编码缓存，量到的只是采样段**（11-09 补，§26 栽的）：编码节点的输入是 clip / vae / prompt /
  `resolution` / 图，**不含 seed**（seed 是 KSampler 的输入）。所以同图同 prompt、只换 seed 的第二发会整个跳过编码 ——
  720p 全量 25.15 秒 vs 只跑采样 19.21 秒，差 6 秒。**要量全量，两发必须换图或换 prompt。**
  而且这个缓存会被"跨档位穿插"挤掉（跑一发别的再回来，量到的也是全量，§26.3）。

### 把"编码"和"采样"拆开的那招

这是这轮最有用的一招，值得单独记：

1. **A 发**：全量。编码 + 采样。
2. **B 发**：整张图**只改 seed**。编码节点的输入（clip 对象、两张图、prompt、`resolution`）一字未动 → 服务端缓存命中，
   于是 B ≈ 只剩采样 + VAE 解码 + 存图。
3. **A − B ≈ 编码那一段。**

关键约束：**prompt 只要变一个字符，整个编码缓存就失效**（11-01 用 A/B/A 三跑验过：151.3 / 145.6 / 56.5 秒 ——
第二发只多了一个空格，时间就从 56.5 弹回 145 那一档）。所以 B 发只能动 seed，别的都不能动。

反过来还有一个坑，**跟上面那条正好是一对**（11-02 晚在远程那台上翻的车，见 §9 末）：
拿"同一句指令、同一颗 seed、只换一个节点的 `class_type`"做 A/B 对照时，如果换进去的那个节点算出来的东西
与前一发**内容相同**，服务端会把整条链按内容重放一遍、只重跑存图 —— 实测第二发报 **0.3 秒**，
出的文件像素与前一发逐位相同、字节只差嵌进去的那段 prompt 元数据。
**那不是速度，是免单**。所以对照实验里两发的指令后缀必须**各不相同**（各加一个没见过的标记），
代价是同 seed 的画面等价性要另开一对去验，不能指望这一对同时给两样。

量冷机同理要打岔：暖机那一发**故意用另一条指令**（加"（暖机）"三个字），让它把三份权重搬进显存、
又不至于把后面 A 发的编码时间提前吃掉。

### 复现脚本

一次性 spike，写在 `/tmp` 里，机器重启就没 —— 关键那几行留在这份文档里，以后照着重写二十行就够：

```python
from tryon import comfy_api, joblock
from tryon.comfy_api import comfy_resolution
from tryon.image_prep import prepare_upload
from tryon.prompt import TRYON_PROMPT

person = prepare_upload(Path(PERSON).read_bytes(), "1k")   # 输入侧两档同上限，prep 一次就够
res = comfy_resolution(person.width, person.height, size)  # 720p→864，1k→0
names = [上传一次记一次，文件名复用 —— 换名字等于换图，比较就不成立]
g_full = comfy_api.build_graph(names[0], names[1:], TRYON_PROMPT, res, SEED, prefix)
g_seed = comfy_api.build_graph(names[0], names[1:], TRYON_PROMPT, res, SEED + 7, prefix)  # 只差 seed
# 分别 POST /prompt 计时；A − B 就是编码
```

## 1. 时间花在哪：1K 那 146 秒的构成（本机，2026-11-02）

| 段 | 本机 8060S | 说明 |
|---|---|---|
| 编码 | **≈ 89.5 秒** | 占全量的 **61%**。`resolution=0` → 1.77M 像素过 qwen3vl 8B 的视觉塔 |
| 采样 + 解码 + 存图 | **≈ 56.3 秒** | 8 步；三发独立测得 56.7 / 56.3 / 56.0（极差 0.7 秒） |
| 权重从内存搬进显存 | 几秒 | 三份共 **17.3 GB**（turbo 7.26 + qwen3vl 9.35 + vae 0.68，`ls` 实数）；空显存冷起比热起只慢 6~7 秒 ≈ 3 GB/s，页缓存命中的量级，不是瓶颈 |

拆出来的数（同机同图，只换 seed 那一发当基线）：

| 档位 | `resolution` | 全量 A | 纯采样 B | 编码 = A−B |
|---|---|---|---|---|
| 720p | 864 | 66.4 ~ 67.3 秒 | 20.1 / 20.2 / 20.6 / 20.9 / 21.0 秒 | **45.7 ~ 46.3 秒** |
| 1K | 0（=1.77M） | 146.0 ~ 146.3 秒 | 56.0 ~ 56.7 秒 | **89.4 ~ 89.6 秒** |

**两条结论，都跟直觉相反：**

1. **1K 档真正贵的是"喂给模型多大的图"，不是"输出多大的图"。** 编码段 89.5 秒 vs 采样段 56.3 秒 ——
   低档之所以省时间，一半是因为采样便宜，另一半是因为 `resolution` 有数了、把参考图压小再喂。
2. README 里那句"**输入多大不影响耗时**"（1.77M / 0.79M / 0.31M 配 544 预算都是 26 秒）**只在预算固定时成立**。
   1K 档走的是 `resolution=0`，输入多大 = 编码多贵。这两句不矛盾，但放在一起容易被读成矛盾，所以写在这。

所以"两个档位独立测出同一个倍数 5.5 / 5.4"这条**作废**，新数两档仍是同一个倍数，但是 **9.5~9.9 倍**。
**为什么差近一倍没解释**：头号嫌疑是那台把视觉特征按内容缓存了，当晚我连着十几发用的都是**同两张图**，
缓存被预热；白天那批是全量头几发。这条挂到 §7。

> **11-02 深夜那台又加了 `--use-ck-attention`：本表远程栏全是"没开那面旗"的数。**
> 开了以后 1K 纯采样 38.2 → **27.5**、全量 → **36.5**，§10 有整套对照（跨机器倍数也因此要再改一次）。

- **差距主要在编码段**（倍数见上面那条更正：两档都是 9.5~9.9 倍，不是当初写的 5.5 / 5.4）。qwen3vl 8B 那颗 9.35 GB 是纯带宽活儿，
  8060S 的 256-bit LPDDR5x 还要和 CPU 分；5060 Ti 是独立 GDDR7。采样段只差 1.5~2.6 倍。
- **16 GB 显存跑得动**：没 OOM、没崩，冷机第一发 21.3 秒就出图（本机等量要 73 秒）。
- 两处已知口径不齐，方向上**对远程不利**：远程 0.37.0（本机 0.43.0）、远程没关预览（本机 `--preview-method none`）。
  所以"5060 Ti 快 3.1~5.2 倍"（更正后的全量比：1K 146.0/47.2、720p 66.6/12.9）这个数里没有偷来的便宜。
- **每格只有 1 发。** 从 720p 到 1K，输出像素多 **2.42 倍**（736×992 → 1152×1536），远程的采样时间多 **4.7 倍**、
  本机只多 2.7 倍 —— 远程随尺寸涨得更快。当时我怀疑是 `QwenImage21Cache` 的 `device=auto` 把前缀缓存推到内存，
  **这个嫌疑在 §8 里被算术基本排除了**（缓存跨 PCIe 读每步只值 1~2 秒，而且方向反了）；
  现在剩下的头号嫌疑是 **16 GB 装下 clip(9.35) + unet(7.26) 后没有余量，DiT 的权重在逐步/逐层地从内存回搬**。
  远程回来先跑 `off` 一发就能把这两者分开：若 `off` ≈ `auto`，缓存那台机器上压根没建，嫌疑只剩搬权重。

## 3. 版本与 attention 后端：省不了时间，但会换图（本机，2026-11-02）

| 配置 | 720p 全量 | 720p 纯采样 | 同 seed 出图（对 0.39+ck 基线） |
|---|---|---|---|
| 0.39.0 + `--use-ck-attention` | 66.6 秒 | 20.9 | — |
| 0.39.0 + `--use-pytorch-cross-attention` | 67.3 | 21.0 | **99.00% 像素有差别，平均每像素差 7.11** |
| **0.43.0 + `--use-ck-attention`** | 66.4 | 20.2 / 20.6 / 20.1 | **0.00%，单像素最大差 0 —— 逐位相同**（PNG 字节数都一样） |
| 5060 Ti（跨机器，同 seed） | 16.4 | 8.1 | 66.56% 有差别，平均每像素差 1.06（1K：67.34%，差 1.66） |

- **升到 0.43 对这条链路是纯版本号**：时间不动，出图逐位相同。
- **换 attention 后端：时间不动（0.6 秒，三发样本都低于两个单发基线，我当作没有），但图换得很厉害。**
  它对结果的影响比换一整台机器还大（平均 7.11 vs 1.06/1.66）。
  **← 这条后半句已被 §12 打到存疑**：同一对后端在 0.43 / 1K 上量到的是 **51.05% / 0.644**，不是 99% / 7.11，
  而且三对后端两两互相吻合在 49~52% —— "换后端"的幅度看起来跟"跨机器"同量级、比"换 seed"小一个数量级。
  0.39 那次的脚本没留下、无法复查，所以**本行的前半句（时间不动）继续有效，后半句以 §12 为准**。
- **"时间不动"只能管本机；而且这里比的两个后端都是融合 kernel，不是"快路 vs 慢路"。**
  11-02 深夜把同一面旗加到 5060 Ti 上，采样段动了 **−28%**（§10）。翻了 0.43 的选路源码才把两台的对照对上：
  `comfy/ldm/modules/attention.py:923-948` + `comfy/model_management.py:528-534` ——
  **本机不加任何 attention 旗时默认就是 SDPA**（gfx1151 正在那张自动开启的名单里，torch 2.14 ≥ 2.7、aotriton 可用），
  `--use-pytorch-cross-attention` 只是把这条路显式写出来；`--use-ck-attention` 是把 `optimized_attention`
  整个换成 `attention_comfy_kitchen_int8`。NVIDIA 那边同理（`is_nvidia() and torch≥2` 自动开 SDPA）。
  所以**两台的对照是对称的**（都是 SDPA → ck），一个 0%、一个 −28% —— 没解释的是**幅度**，不是选路事故，
  也别据此说"ck 在 A 卡上没用"，本机从没跟**真慢的那条**（`attention_basic` / `attention_sub_quad`，einsum 全量矩阵）比过。
  源码证据我没用启动日志核实过（那台的日志我看不到），要钉死就把它关回默认再跑一对 A/B。
  图的对照也一样：同 seed 同指令只换后端，远程是 **56.7% 像素有差别 / 平均每像素差 0.757 / 单像素最大 113**，
  比本机的 99% / 7.11 温和得多，倒是跟跨机器那一格（66.6% / 1.06）同量级。
- **`--use-ck-attention` 走的是 int8 量化的 attention —— 所以"换后端换图"是有损，不是等价实现的尾差。**
  `attention_comfy_kitchen_int8` 调的是 `comfy_kitchen.int8_attention(q,k,v,...)`，只有传
  `low_precision_attention=False` 且 q 是 fp32 时才回落到 SDPA。上面那两格像素差因此有了机制，
  也说明一条：**"逐位相同"这种验收标准不能跨后端用**（同 seed 同图同参数，换个 kernel 就不是那张了）。
- 所以那条推论要写死：**seed 不是"重出一模一样那张"的把手。** 换后端、换机器都会改写细节（袖子卷不卷这种），
  构图 / 脸 / 姿势 / 门牌倒是稳的。想留住某一张，只能留住那张文件。
- 后来在 1K 上又补了一条后端（sage-int8）与一条**"只换 seed"**的控制：sage **反而慢 6.6%**、而"只换 seed"与本表
  那条"换后端 99% / 7.11"同档 —— 两件事都在 §11，那里也把"99% 不是后端的签名"写清楚了。
- 顺带更正一处算法：我一开始报"跨机器约 80% 像素不同"，那个百分比把三通道拼在一起的直方图里第 2、3 通道的
  零值桶（索引 256、512）当成差值算进去了，任何两张图都会白送 66.7%。上表是按"每像素三通道取最大差"重算的。

## 4. 官方工作流 vs 我们那张图（2026-11-01）

对象：`workflow_templates` 里的 `image_qwen_image_2_1_image_edit.json`（8 个外层节点 + 1 个子图 13 个内部节点）。

- `refine_prompt=off`、`custom_size=off` 时，官方那张图**归约后与我们同构**：`UNETLoader → QwenImage21Cache → KSampler`、
  `CLIPLoader → TextEncodeQwenImage21`、`VAELoader` 同时喂编码与 `VAEDecode`，latent 走编码节点输出。
  实测证据：**leg3（官方全形 + 我们的 turbo/8 步，同输入同 seed）跑完只用 1.0 秒**，`nodes_that_ran` 只有
  `461`（SaveImageAdvanced）和 `480`（PreviewAny）—— 前面全被服务端缓存服务掉了，说明两个计算图逐项对得上。
- **PE（Prompt Enhancement）那条分支确实没执行**：`ComfySwitchNode` 的 `on_true`/`on_false` 在 schema 里写着 `"lazy": true`，
  `comfy_execution/graph.py` 里 `add_node(include_lazy=False)` → 未选中的分支不进依赖图。
  但**验证阶段仍要求那条分支所有节点控件齐全**（`execution.py` 遍历 `valid_inputs`）—— 摆进图里就得给全，哪怕永不执行。
- **`refine_prompt` / `thinking` / `max_length` 这三个控件不在我们的节点上。**
  `TextEncodeQwenImage21` 的 `/object_info` 只有 `clip / prompt / negative_prompt / resolution(默认1024,0–4096,step32) / images(autogrow≤16)`，
  可选 vae；输出 CONDITIONING, CONDITIONING, LATENT。那三样在模板里是**外层子图实例的 widgets**：
  `refine_prompt` / `custom_size` 是两个 `ComfySwitchNode` 的开关，`thinking` / `max_length` 往下喂给 PE 分支的 `TextGenerate`。
  也就是说：**"要不要开 refine prompt / thinking"这个问题在我们这张图上没有意义** —— 我们从头到尾没接 PE 那颗模型。
  PE 权重（`qwen3.5_9b_qwen_image_2.1_pe_i2i.int8_convrot.safetensors`，9.47 GB）在本机 `models/text_encoders/` 里躺着，从未被引用；
  它那条链的系统提示光模板里那份就有 10494 个字符。
- **官方默认（base 权重 + 25 步）不省时间**：leg2 实测 **158.4 秒**，我们 turbo + 8 步同输入 **146.2 秒**（同 seed、同 resolution=0）。
- v3 节点的 API 写法两个坑（少一个就是整份图 `prompt_outputs_failed_validation`）：
  dynamic combo 的嵌套控件是**点号平铺键**（`format.bit_depth`、`sampling_mode.temperature` 这种，不是嵌套字典）；
  autogrow 前缀命名不统一 —— `BatchImagesNode` 是 `images.image0` 起自 **0**，`TextEncodeQwenImage21` 是 `images.image_1` 起自 **1**。

## 5. 那个文本编码器是什么（顺带钉死）

`CLIPLoader(clip_name="qwen3vl_8b_int8_convrot.safetensors", type="qwen_image")` —— **Qwen3-VL 8B**，不是 CLIP 也不是 T5。

- 调用链：`comfy/sd.py` 2.1 分支 → `comfy/text_encoders/qwen_image21.py`（`model_type="qwen3vl_8b"`、
  `thinking=True` 默认、`layer_norm_hidden_state=False`）→ `qwen3vl.py`（`embedding_size=4096`、`tokenizer_class=Qwen2Tokenizer`）。
- 取的是**最后一层 hidden state 且不加最终 RMSNorm**（注释说对齐 transformers 4.57 的 `hidden_states[-1]`）。
- **参考图是从它走的**：`TextEncodeQwenImage21` 把每张图按 `resolution` 重采样后塞进视觉塔（模板里插 `<imageN>` + vision block），
  conditioning 里文字 token 和图像 token 混在一条序列上 —— 所以 §1 那 89.5 秒、§2 那 5.4 倍差距都是它。
- **它看到的提示长这样**（`qwen_image21.py:8-24`，我们无法从图上改）：system turn 固定一句
  `Comprehend and analyze the provided prompt.`，user turn 里先拼 `refs` 再接我们的指令，末尾开 `assistant`。
  `refs = "<image1> …<image2> …"` —— 序号就是**槽序**（第 i+1 张），所以指令里那句中文"图像2"**必须**跟它对齐：
  人像恒 1 号、参考图按槽序往后排，插队会让文字指的和第 2 个 vision block 装的东西不是同一张。
- 本机 `models/text_encoders/` 里另有 PE 那两颗 9B（`qwen3.5_9b_…_pe_t2i` / `pe_i2i`，各 9.47 GB）和 `qwen3vl_32b_…`（27.14 GB），
  我们一个都不引用 —— 那是 `refine_prompt=on` 那条分支的活（§4）。

### 编码段是谁花的（1K = `resolution=0`，两张图按原尺寸喂）

| 段 | 正向 | 负向 | 合计 | 占编码 |
|---|---|---|---|---|
| **视觉塔**（Qwen3-VL 的 ViT） | 20.62 + 11.27 = 31.9 s | 20.62 + 11.28 = **31.9 s** | **63.8 s** | **71%** |
| **8B 主干**整趟 | 12.79 s（seq 2865） | 12.52 s（seq 2771） | 25.3 s | 28% |
| VAE 编两张参考图 | — | — | 1.0 s | 1.1% |
| resize（lanczos） | 0（1K 走不缩放分支）；720p 是 58 ms | | | |
| **一趟合计** | **44.68 s** | **44.43 s**（`chars=0`） | **90.1 s** | 100% |

对账：墙钟 A−B = 145.3 − 55.0 = **90.3 秒** ✓。720p 同法：视觉塔 31.6 / 8B 14.4 / VAE 0.9 / 编码共 47.0 秒（墙钟 A−B 45.7~46.3）。
探针自己几乎不额外耗时：8189 上 1K 的 A/B 是 145.3 / 55.0，8188 干净实例是 146.0~146.3 / 56.0~56.7。

**两条读码结论被实测钉死，而且都很大：**

1. **负向那一整趟 44.4 秒 = 一次 1K 请求（144.9 秒）的 31%，而 `cfg=1.0` 下采样器永远不用它。**
   我们传的 `negative_prompt` 是空串，节点照样把两张参考图**又过了一遍视觉塔**（31.9 秒）再走一遍 8B（12.5 秒）。
   省不掉的根源是"正负两次编码在同一个节点里"，图上怎么接线都改不了。
2. **视觉塔的产出算完就被扔掉。** 1K 正向：`cond_before=2865 → dropped=2750`，
   **真正进 DiT 的 conditioning 只有 115 个 token**（负向 21）。图像条件是走 VAE latent 进去的。
   人像 6912 个 patch（grid 96×72）→ 合并后 1728 token，衣服 4032 → 1008 token，这 2736 个就是被丢的那批。

顺带把进 DiT 的 token 账也量了（§2 与下面那个"缓存值多少"都靠它）：**目标 6912 token，参考图 latent 10944 token** →
前缀 ≈ 11,059 = 目标的 **1.60 倍**（720p 是 5849 / 2852 = 2.05 倍）。

### `QwenImage21Cache`：device × dtype 六发（1K，编码已缓存，只动这两个控件 + 同一颗 seed）

| 组合 | 采样段墙钟 | 出图 vs `gpu-default` |
|---|---|---|
| `leg0`（`auto`/`default`，全量含编码） | 144.9 s | 不同 seed，99.48% 有差别、均值 8.37（**说明这套指标对换 seed 很敏感**，下面的 0.00% 不是失灵） |
| `gpu` / `default` | **55.1 s** | — |
| `gpu` / `int8` | 56.5 s（+1.4） | 47.69% 有差别，均值 0.599，单像素最大 112 |
| `gpu` / `int4` | 58.2 s（+3.1） | 66.66% 有差别，均值 1.502，单像素最大 196 |
| `off` / `default` | **103.6 s** | **0.00%，逐位相同** |
| `off` / `int8` | 104.5 s | **0.00%，逐位相同**（off 三行彼此也是 0.00%） |
| `off` / `int4` | 105.3 s | 同上 |

四条：

1. **这个 prefix 缓存值 1.88 倍采样时间**（103.6~105.3 → 55.1）：1K 档每请求省 **48.5 秒**，占整次请求的 33%。
   token 账能对上：设每步前缀成本 P、目标 T，缓存省的是 7P ⇒ P = 48.5 / 7 ≈ **6.9 秒** —— 也就是
   **"不重置 prefix cache、跨请求留着"最多再值 6.9 秒（4.8%）**，只有"负向白跑"那 44.4 秒的六分之一。
2. **缓存是精确的，不是近似**：`gpu-default` 与 `off-default` 出图**逐位相同**（代码里那句"prefix 行按 t=0 调制"成立）。
   所以开缓存不换图，这是它敢默认开的实证。
3. **`device=off` 时 `dtype` 真的不被读**：off 那三行逐位相同 ✓（与读码一致）。
4. **`auto` 在本机 = `gpu`**（55.1 vs 之前的 55.0），显存充裕时它确实放进了显存。**量化在这台机器上是纯亏**：
   int8 慢 1.4 秒、int4 慢 3.1 秒，还各掉一档细节。它们的用途在"内存吃紧"的卡上，不是这里。

缓存体积按实数算：`L=32`、`inner_dim=4096`（从 turbo 文件头读出来的张量形状），前缀 11,059 token，bf16
⇒ 每个 conditioning `2 × 32 × 11059 × 4096 × 2 B = 5.81 GB`，正负两份 = **11.6 GB**。
`auto` 的建缓存门槛是"空闲显存 > 4 × 体积"= 46.5 GB —— 本机 124 GB 统一内存过，**16 GB 的 5060 Ti 不可能过**，
只能退到"挪不活跃的模型内存做 host cache"那条分支（那台机器空闲内存 18.5 GB，也紧）。
但跨 PCIe 每步读 5.8 GB 只值 1~2 秒，撑不起 §2 那个 4.7 倍，**而且方向是反的**（720p 的前缀/目标比是 2.05，
比 1K 的 1.60 更大，缓存缺失更该伤 720p）—— 所以 §2 那条嫌疑改判：**头号嫌疑是 16 GB 上 DiT 权重逐步回搬**，
远程回来跑一发 `off` 就能分开（`off ≈ auto` ⇒ 那台上缓存根本没建）。

## 13. 编码段还能怎么砍：重试其实已经免费了，剩下的肉在"视觉塔吃多大"（本机 0.43 + fork，2026-11-03）

|---|---|---|

| D | 重试：同图同指令，只换 seed | **54.8** |
| E | 重试：**同样的字节再上传一次**，换 seed | **54.8** |
| F | 再重试：不重传，第三颗 seed | **54.9** |

E 是这条的关键，也是**我原本猜错的地方**：我以为 `tryon/comfy_api.py:197` 每次重试都重新上传会被
`server.py:497-503` 改名成 `person (1).jpg`（那样缓存 key 就变了、整趟编码重烧），实测**没有**：

三条会把这个免费午餐打破的边界（前两条实测、第三条按 key 语义推定）：
1. **换档位会重烧**：`resolution` 是编码节点的输入，720p 那对（G/H）= **43.5 = 23.0 编码 + 20.5 采样**，

2. **换图 / 换指令就是新内容**（本来就该重编）。
3. **进程重启缓存清零**（PM2 重拉、崩溃、`--cache-*` 被显存压力挤掉都会）—— 首张那 101 秒付的就是这个价。

**二、`resolution` 这一个数同时管着三件事，所以"少喂像素"没法用现成旋钮做。**
读 fork 的 `comfy_nodes/qwen21_posonly_encode.py:74-108`：同一个 `resolution` 决定 ① 每张参考图过
lanczos 的目标尺寸（⇒ 视觉塔的像素，也就是 §8 那 31.9 秒）、② 送进 DiT 的 `reference_latents` 尺寸
（10,944 个 token 的来路）、③ latent 画布 = **输出分辨率**（92-93 行：取第一张图的 resize 结果）。
`1K` 档传的是 `0` = "按各自原尺寸"，所以人像 1.77M 原样进塔。

这次探针顺手纠正一个可能的误读：G/H 那两发的上传尺寸**与 1K 完全相同**（都是 1152×1536），
编码却还是从 46.2 掉到 23.0 —— **省的全在节点内部的 resize**，不是上传图变小。§1 那句"低档把参考图压小再喂"
说的是这件事，别读成"prepare_upload 压小就够"。

于是编码段剩下的可动项只有两个层次：

| 目标 | 现值（1K，fork 后） | 能压到 | 办法 |
|---|---|---|---|
| 视觉塔 | **31.9 s**（占编码 69%） | ~15.8 s | 给视觉塔单独一个小预算（`resolution` 保持 0 出 1K，`images_vl` 按 864~1024 resize） |
| 8B 主干 | **12.8 s**（28%） | ~7.2 s | 同上顺带 —— 它的 seq 长度 2865 里绝大部分就是那批视觉 token |
| VAE 编两张参考图 | 1.0 s | — | 不动 |

按 §8 的 720p/1K 两档实测值折算，"只压视觉输入、不动输出与 reference_latents"这一刀的量级是
**编码 46.2 → 23~30 秒**（全量 101 → 78~85，**−16%~−23%**）。
可行性上它比 §9 那刀更"有争议"：视觉塔的产出算完就被丢（§8：`cond_before=2865 → dropped=2750`，
进 DiT 的只有 115 个 token），**但它没有被白算 —— 那 2736 个 token 是 8B 生成这 115 个 token 时"看见"的图**。
压小它 = 让文本条件少看细节，**画质影响必须人眼评，不能只看墙钟**。这条还没做。

## 14. Spike：同一颗 APU 上 llama.cpp 的视觉塔快一个数量级 —— 但成败不在速度（2026-11-03）

动机：§13 之后编码段只剩"视觉塔 31.9 + 8B 主干 12.8"。提出的路子是改用 llama.cpp 载 Qwen3-VL 8B，
赌它在**缓存管理与 kernel 速度**上都强过 ComfyUI 自带的引擎。**这一步先不动任何集成，只量 kernel 差多少。**

代理测法（**模型不是同一颗**，所以是量级指示，不是判决）：`~/work/llama/llama-b12063-rocm/llama-mtmd-cli`
（b12063；日志 `loaded ROCm backend …/libggml-hip.so`、`using device ROCm0 (AMD Radeon 8060S Graphics) - 104706 MiB free`、
`offloaded 66/66 layers to GPU`）载 `Qwen3.8-27B-UD-Q4_K_XL.gguf`(17.9 GB) + `mmproj-Qwen3.8-27B-BF16.gguf`(0.93 GB)，
`--flash-attn on --mmproj-offload --image-min-tokens 1024`，输入就是那张 **1152×1536 人像**。

| 项 | llama.cpp（27B Q4 + **bf16** ViT） | ComfyUI（8B int8，§8 实测） | 每 token 之比 |
|---|---|---|---|
| 视觉塔：人像 1728 合并 token | **1.93 秒** = 1.12 ms/tok | 20.62 秒 = 11.93 ms/tok | **≈10.6×** |
| 视觉塔：衣服 1008 token | **0.88 秒** = 0.87 ms/tok | 11.27 秒 = 11.18 ms/tok | ≈12.8× |
| LLM prefill | 6.10 秒 / 1746 tok = **3.50 ms/tok** | 12.79 秒 / 2865 tok = 4.47 ms/tok | ≈1.3×（而权重是它的 **2 倍**） |
| 建模/载入 | load 14.65 秒（18 GB，页缓存） | §1：17.3 GB 冷起只慢 6~7 秒 | — |

对账上了才敢比：llama.cpp 报 `image_tokens->nx=36, ny=48` → **1728 个合并 token**，与 §8 在 ComfyUI 侧量到的
"人像 6912 patch（grid 96×72）→ 合并 1728"**完全一致** ⇒ 两边是同一套 vision merge 数学。

**粗投射**（把 kernel 效率搬到我们自己的 token 数上，VAE 那 1 秒留在 ComfyUI）：
1K 编码 44.7 秒 → **约 2.8 + 6~7 ≈ 9~10 秒**，1K 全量 102 → **约 65 秒（−36%）**。这比 §9 那一刀还大。

**先排掉两个"其实是配置问题"的解释**：ComfyUI 侧**没有 CPU 回退**（PM2 日志 `fallback` 0 条）、
文本编码器**在 GPU 上跑 fp16**（`text_encoder_device=cuda:0`、`text_encoder_dtype=float16`）；
而且编码段随像素**近似线性**（864 → 23.0 秒、1.77M → 46.2 秒；token 比 2.36、时间比 2.0），不是平方级注意力的形状。
⇒ 那 10 倍是**实现（kernel）差距**，不是算法差距，也不是硬件。

**三条能让这事做不成的前提**（按致命程度排）：
1. **语义**：§5 钉过 conditioning 取的是"**最后一层 hidden state 且不加最终 RMSNorm**"（`layer_norm_hidden_state=False`）。
   llama.cpp 的 embedding 出口一般已经过 output norm —— 拿不到 pre-norm 向量，DiT 收到的就是另一种条件。
   **这是代码层问题，不是配置能解决的**，也是这整个想法的生死线。
2. **权重**：我们的 `qwen3vl_8b_int8_convrot.safetensors` 是 ComfyUI 的 int8 convrot 格式，
   `llama.cpp/conversion/qwen3vl.py`（支持 qwen3vl，已确认存在）要的是 HF 原格式。
   要么下 HF bf16（~17 GB）自转 GGUF+mmproj，要么取社区 GGUF（~7 GB 含 mmproj）——
   **换量化就等于换 conditioning、换图**，必须人眼评，不能只看墙钟。
3. **拼接**：system 那句固定英文、`<image1>/<image2>` 的**槽序**、`vision block` 插入位置、`thinking=True`、
   以及"2736 个视觉 token 全丢、只留 115 个文字 token"那套裁剪（§8）都得在 llama.cpp 侧复现。token 算术已对上，所以可做，但没捷径。

**关于"缓存管理"那一半的赌注**：llama-server 常驻 + 自家 KV/RAM 缓存，确实能覆盖 §13 那条"进程重启缓存清零"的边界
（ComfyUI 的节点缓存是进程内的）。但 §13 已量到**同图同指令重试本来就免费**（101.0 → 54.8），
所以这条只在"重启后的第一发"与"跨档位"两种情形里挣钱，不是主收益。

**下一步有两条便宜的路，我建议先走第二条**：
- **判死实验**：拿到 Qwen3-VL-8B 的 GGUF+mmproj 后**先别写节点**，同图同指令比两边逐 token 向量的余弦。
  若连"norm 之后的版本"都到不了 0.99，这条路到此为止，省下后面全部工程量。
- **更便宜的那条**：既然 10 倍是 kernel 差距，ComfyUI 侧也可能有就地修法（视觉塔的 attention 实现、
  upcast 选项、换 dtype 的权重文件而非 int8 convrot）。**先查这个再做移植**，工作量差一个量级。

现场：这条 spike 只读了 `~/work/llama` 与 `~/work/models`，没装东西、没改 llama.cpp、没动 ComfyUI（仍是 `--use-ck-attention`），

## 15. 找到本机的了：AMD 上 ComfyUI 默认关掉 cuDNN，patch_embed 那个 Conv3d 慢 23000 倍（2026-11-03）

接着 §14 第二条路（"先查能不能就地修"）走通了，而且赢的是**一个环境变量**。

### 归因链（含两次我自己量错的地方）

1. **op 级归因**（真权重、真 ops、逐叶子模块计时，`/tmp/vit-prof/prof7.py`）：整趟编码 46.61 秒里
   **`Conv3d (patch_embed)` 两次调用共 25.98 秒 = 55.7%**；视觉塔 27 层的**全部** Linear 加起来才 1.01 秒，
   LayerNorm 0.04 秒，剩下 ~19.6 秒是 8B 主干。所以 §8 说的"视觉塔 31.9 秒"里，**大头不是视觉塔，是它第一层的卷积**。
2. **那个卷积在数学上就是个矩阵乘**：`Qwen35VisionPatchEmbed`（`qwen35.py:598-603`）把输入 view 成
   `(-1, C, T, P, P)`，而 kernel 与 stride 都是 `(T, P, P) = (2,16,16)` —— 无重叠，等价于
   `x.reshape(N,1536) @ W.reshape(1152,1536).t() + b`。同权重同输入实测：**Conv3d 16538 毫秒 vs GEMM 0.80 毫秒**。
3. **两次假信号，都记下来免得再踩**：
   - 我第一版 replica 把 NHWC 张量又 `permute(1,2,0)` 了一次 → 喂进去的是被压扁的破图（grid 只有 140 patch，
     真实是 6912），于是"随机权重只要 0.38 秒"是假的。
   - ComfyUI 这些模块的 `reset_parameters()` **返回 None**（`ops.py:674-675`），所以 `Qwen3VLVisionModel(...)`
     随机建出来的模型权重是**未初始化的垃圾位**，也量不出真东西。
   两条都靠"真权重 + 真形状"那版（prof7/prof9/prof10）才立住。
4. **进程级二分**（`prof10.py`）：同一个 Conv3d，只 `import torch` 时 0.70 毫秒，
   **一旦 `import comfy.model_management` 就变 16538 毫秒**。原因是 `comfy/model_management.py:486-490`：
   AMD 上除非 `COMFYUI_ENABLE_MIOPEN=1`，ComfyUI 会设 **`torch.backends.cudnn.enabled = False`**
   （原注释 "Seems to improve things a lot on AMD"）—— 于是这个卷积走 PyTorch 原生参考实现。
   `cudnn.benchmark`  True/False 都一样慢，**不是 autotune 的问题**。

## 18. llama.cpp 判死实验：LLM 那一半是同一套数学，图像进去之后不是（2026-11-03，Vulkan b12063）

§14 挂的那条"先别写节点，同图同指令比逐 token 向量余弦"，今天做完了。脚本都在 `/tmp/q3vl-gate/`：
`cond_comfy.py`（参照侧落盘）、`stage0.py`（分词）、`with_images.py` / `probe_llama.py`（llama 侧）、
`compare_text.py` / `compare_images.py`（判读）。后端按 denvor 的要求先走 Vulkan（`~/work/llama/llama-vulkan`，
与 ROCm 那份同为 build 12063 / commit 2cbca389f；他说两边速度基本一致，对拍留给以后）。

**第 0 关 分词：过。** 照 `qwen_image21.py` 的常量重建那句字面模板（system 固定句 + `<imageN>` + vision block +
`assistant` 收尾），`llama-tokenize` 与 ComfyUI 分出 **117 个 token、逐位相同**（有无 `--no-bos` 都一样 —— 这颗没 BOS）。
⇒ GGUF 词表 == ComfyUI 那份 `Qwen2Tokenizer`，且我重建的模板就是 ComfyUI 真正喂进去的字节。

**通路（这些都值得记，查了三轮才通）**
- 逐 token 向量的口子是 `llama-server --embeddings --pooling none --embd-normalize -1` + **老式 `POST /embedding`**；
  `/v1/embeddings` 在 pooling=none 下直接 400（`Pooling type 'none' is not OAI compatible`）。
- **图片必须用 OAI 的 `content` 分块**（`{"type":"text"}` / `{"type":"image_url","image_url":{"url":"data:..."}}`），
  让 server 自己插媒体标记。自己往文本里插标记这条路是死的：`<__media__>` `<image>` `` `
  `[image]` `{{image}}` `<|img|>` **九种全报 `number of media markers in text (0)`** —— 那条路径压根不扫你给的串。

## 20. 那两条 MIOpen export：`MIOPEN_ENABLE_CACHE` 这个变量不存在，`MIOPEN_FIND_MODE=FAST` 砍的是"新形状第一次"，代价是 VAE 换了内核（2026-11-03）

起因是 denvor 给的两条 `export`（`MIOPEN_FIND_MODE=FAST` 说能加快首次运行、`MIOPEN_ENABLE_CACHE=1` 说能"启用缓存，避免每次都重新调优"），让我先试试。

**三条结论，先说**
1. `MIOPEN_ENABLE_CACHE` **在 MIOpen 里根本没有这个名字**。它想达到的那件事（别每次重新调优）**一直是开着的**，不需要它。
2. `MIOPEN_FIND_MODE=FAST` 是真开关，但它**只管"这台机没见过的卷积形状"**：稳态一分钱不省（我们记的那 73.2 秒不会变），
   省的是"第一次遇到某个形状"的那笔调优 —— 实测一趟 1K 的编码 + VAE encode + VAE decode，**冷 db 要 131 秒，FAST 30 秒**。
3. 代价量到了，不是猜的：FAST 之下 **VAE 的 latent 与解码像素逐位不同**（编码那份反而四臂逐位相同）。
   但**量级我一开始判重了**：端到端是"54% 像素逐位不同"里只有 **0.70%** 的像素通道差过 16、PSNR 36.36，
   人眼看是同一张图的细节差一档（差别在袖口卷起程度），不是两张图 —— 分级与判读在 §22，处置在 20.6。

### 20.1 变量存不存在，问库，不要背文档

```bash
strings -n 8 /opt/rocm/lib/libMIOpen.so.1.0 | grep -E '^MIOPEN_[A-Z0-9_]+$' | sort -u
```

这台机（ROCm 6.x / MIOpen 3.6.1 / torch 2.14.0+rocm10.1.0）一共认 428 个 `MIOPEN_*`，里面有
`MIOPEN_DISABLE_CACHE`、`MIOPEN_CUSTOM_CACHE_DIR`、`MIOPEN_USER_DB_PATH`、`MIOPEN_SYSTEM_DB_PATH`、
`MIOPEN_FIND_MODE`、`MIOPEN_FIND_MODE_FUSION`，**没有 `MIOPEN_ENABLE_CACHE`**（值名 `NORMAL FAST HYBRID DYNAMIC_HYBRID NONE` 五个都在库里，所以 `FAST` 这个词是能解析的）。写了不存在的名字，MIOpen 不报错、不警告，就是没效果。

`find` 那一档的口径（ROCm 官方 *Using the find APIs and immediate mode* 页，与下面实测对得上）：

| 值 | 干什么 |
|---|---|
| `NORMAL` | 把这个形状的候选内核**全跑一遍**，选最快的，结果写进 user find-db |
| `FAST` | 查 find-db，命中就用；**没命中就直接按启发式（AI 网络 / 吞吐索引）点一个，不试跑** |
| 不设 | 这台机上实测与 `NORMAL` 一模一样（20.2 那四行的墙钟与 sha 全部相同） |

另外核实两件：① 正在跑的 8188 服务进程 `environ` 里只有 `COMFYUI_ENABLE_MIOPEN=1`，没有任何 `MIOPEN_*` 选核变量，
ComfyUI 与 torch 的代码里也没有一处设 `MIOPEN_FIND_MODE` ⇒ 今天这台机跑的就是默认档；
② **"缓存"确实一直在生效** —— `~/.config/miopen/gfx115128.HIP.3_6_1_39d8d603.ufdb.txt` 有 428 行调优结果，
最后更新 11-03 14:27（就是我们上一趟跑完写的）。文件名里带着 `HIP.3_6_1_39d8d603`，
**换 ROCm / MIOpen 版本就是换一个文件名 = 这 428 行整体作废 = 冷账重付一遍**。

### 20.2 微基准：一个"新形状"值多少秒（`/tmp/mio/findbench.py`，不加载任何模型，十秒级）

形状故意挑系统 db 里不可能有的怪尺寸（奇数 H/W、非常规通道），保证走 miss 路径；`cudnn.benchmark=False`（与生产一致）。

| 形状 | 不设（=今天生产） | `FAST` | 稳态耗时 不设 / `FAST` | 输出 sha256（不设 → `FAST`） |
|---|---|---|---|---|
| 3D 2→24ch kernel 4x14x14 | 423 ms | 385 ms | 0.2 / 0.2 ms | 相同 |
| 3D 96ch 3x3 s2 | **481 ms** | **19 ms** | 3.4 / 3.4 ms | 相同 |
| 3D 192ch 3x3 | **3187 ms** | **20 ms** | 11.3 / 11.5 ms | 相同 |
| 2D 64→128ch 3x3 s2 | 63 ms | 5 ms | 0.4 / 0.4 ms | **不同**（`141dd93e` → `11b8aa01`） |

- 省的就是**每个新形状第一次**的 0.06 ~ 3.2 秒，别的一律不动（稳态那一列四行全等）。
- `FAST` **不往 find-db 写任何东西**：`db-fast/` 跑完是空的，而不设那臂写了 4 行。所以一开 `FAST`，
  这台机就不再攒调优结果了，每次进程起来都重新猜一遍（猜得很快，但也永远不验证）。
- 最后一行是这次唯一一处"选到不同内核"：2D 卷积那条 `FAST` 的启发式点了一个与调优结果不同的解，输出逐位就变了。
  这个项目里"逐位不同"意味着什么，§15 已经给过答案（那次只换了卷积实现，同 seed **63% 像素不同**）。

| 热 db，不设（=今天生产） | 3.57 s | **20.25 s** | 0.96 s | 2.32 s | 32 s | `56c71779` / `342512b4` / `e6549f06` | 428（没长） |
| 冷 db，不设 | 3.43 s | **59.02 s** | **21.57 s** | **42.76 s** | **131 s** | `56c71779` / `342512b4` / `e6549f06` | 74（这一趟新增） |
| 冷 db + `FAST` | 3.35 s | 20.34 s | 0.97 s | 2.15 s | **30 s** | `56c71779` / **`6709beb3`** / **`901ee592`** | **0** |
| 热 db + `FAST` | 3.55 s | 20.35 s | 1.03 s | 2.17 s | 31 s | `56c71779` / `342512b4` / `e6549f06` | 428（没长） |

六条读法：

1. **编码段那 +38.8 秒是纯调优，不是算错**：四臂的 `cond_sha` 完全相同（`56c71779…`，2851×4096 那份）。
   也就是说 Qwen3-VL 这一路（patch_embed 的 Conv3d 家族，db 里 `2x16x16` 一族有 10 个尺寸）不管怎么选核，
   条件向量都是同一份字节。
2. **冷 db 的账主要在 VAE**：VAE encode +20.6 秒、decode +40.4 秒，比编码段那笔还大 ——
   db 里 `NCDHW` 的 `1x3x3` 有 249 个、`1x1x1` 有 76 个，全是这颗 3D VAE 按分辨率长出来的形状。
3. 三段加总 +99.8 秒，与总墙钟 131 − 32 = **99 秒**对得上 ⇒ 冷 db 那一趟里，**第一次跑的三分之二时间在调优**。
4. **`FAST` 把这笔整体免掉**（131 → 30 秒，且 30 秒里还包含 3.35 秒载入），冷 FAST 与热默认在时间上不可区分。
5. **但 VAE 换了内核**：冷 `FAST` 那臂的 latent 是 `6709beb3…`、像素是 `901ee592…`，与另外三臂的
   `342512b4…` / `e6549f06…` 逐位不同。⇒ 一台从第一天就开 `FAST` 的机器，它的 VAE 属于**另一套数值制度**。
6. **`FAST` 只在 miss 上起作用**，这一点被第四臂钉死了：热 db + `FAST` 与热 db 不设**逐位相同**。
   所以对这台已经攒满 db 的机，今天开 `FAST` 不改任何输出 —— 但因为它不写 db，
   **今后的新形状会一批批落到启发式内核上**，同一台机器上会混着两套数值，而且没人会注意到是哪一批。

顺带一条与线上体验直接相关的：这一趟 1K 只新增 74 个形状，而真 db 攒了 428 个 ——
`428 − 74` 是别的档位/别的图片尺寸攒下的。用户传来的照片尺寸是**不被 4 个档位约束的**（编码节点按 32 取整），
所以默认档下"新形状"会持续零星出现，每个 0.5 ~ 3 秒，落在一发 73 秒的请求里不显眼，但它是真实存在的第一发抖动。

### 20.4 我的判断（不是数）

- **`MIOPEN_FIND_MODE=FAST` 这件事别默认开着，但它没有我一开始说的那么贵**（判断订正见 §22 第 2 条与 22.1）：
  省的是每个新形状第一次的那笔调优（端到端第一发 192 → 82 秒），代价是**从此失去逐位复现能力** ——
  整体 PSNR 36.36、只有 0.70% 的像素通道差过 16，人眼看是"同一次试穿的另一个细节版本"（差别在袖口卷起程度），
  不是两张不同的图。**所以真正的问题不是"会不会崩画质"，而是"你要不要保留两张能对齐的图"** ——
  比如以后要拿历史图做前后对比、或者要拿同 seed 判一次改动的影响，开了 FAST 就没法做了。
  要判，翻 22.1 那七份自己看。
- **该做的是预热，而不是换选核策略**：上线前四档各打一发（TODO §3 那条），本质就是在替用户付这笔调优费 ——
  现在有了价签：**每档第一次约贵 100 秒**（1K 实测 131 vs 32 秒，只算编码 + VAE 三段）。
- **db 是 90 KB 的文本文件，可以随发布带走**：`~/.config/miopen/*.ufdb.txt` 拷到目标机（或给它设
  `MIOPEN_USER_DB_PATH` 指到仓库里一份签好的），部署机就不用在自己身上现攒 —— 比 `FAST` 干净得多，
  因为它改的是"钱什么时候付"，不改"结果是什么"。
- **确认部署用户能写那个目录**：写不了的话不是"少攒点缓存"，而是**每一发都重新调优**，比冷 db 更糟。
- **`export MIOPEN_ENABLE_CACHE=1` 那行删掉**，别在 `start.sh` 里留一个假开关：下一次有人以为它开着，就会拿它解释一段实测。
- 这两条都不解决 §15 那个根子问题（AMD 上 cuDNN 被默认关掉），它们只管 MIOpen 内部的选核，
  `COMFYUI_ENABLE_MIOPEN=1` 仍然是这台机上最值钱的那一条。

### 20.5 find-db 到底是什么、活多久（denvor 问"这东西重启总还在吧"，答：在，但有几个作废条件）

**它就是一个纯文本台账**：一行 = 一道卷积题 + 这台 GPU **实测**各候选内核跑它要多少毫秒。有这行就不用再拿真数据试跑；
没这行（miss）就现场把所有候选跑一遍 —— 那笔钱就是 §21 的 124 秒。

```
~/.config/miopen/gfx115128.HIP.3_6_1_39d8d603.ufdb.txt        90 KB / 428 行
```

键那半（`…-NCDHW-BF16-F=` 之前）是这道题的全部参数：编码塔的 `3-2-16-16-2x16x16-1152-…-6912-…` 就是
输入 3 通道 × 2 帧（`temporal_patch_size=2`）× 16×16（`patch_size=16`，`comfy/text_encoders/qwen3vl.py:19`）、
核 `2x16x16`、输出 1152、**6912 个 patch**（= §8 那个"人像 6912 → 1728"）、padding/stride/dilation 与布局精度。
值那半是 `内核名:实测毫秒,workspace 字节,算法标签`，分号分隔。
**一个顺手量出来的坑：这个列表的顺序不是名次** —— `96-1537-1153-3x3…` 那行第一个 `GemmFwdRest:9.82ms`
比第二个 `…Xdlops:8.39ms` 慢。所以别拿"行里第一个"当"被选中的"，它没标谁中选。

分三层，别再混着说"缓存"（我在这一轮里就说糙过一次）：

| 是什么 | 在哪 | 谁写 |
|---|---|---|
| **user find-db**（本机调优台账，上面说的那份） | `~/.config/miopen/*.ufdb.txt` | 本机跑到 miss 时追加，可写 |
| **system find-db**（AMD 预置，只读） | `/opt/rocm/share/miopen/db/gfx115128.HIP.fdb.txt`（1.1 MB：4309 条 NCHW + 686 条 NCDHW） | 装 ROCm 时带来 |
| **内核编译缓存**（另一回事：存编译好的内核，不存"选哪个"） | `~/.cache/miopen/3.6.1.39d8d603/gfx1151_20.ukdb`（209 KB） | 第一次要用某内核时 |

**存活：跟进程、服务、开机都无关，只跟盘有关。** 这台机上这份 428 行从 14:27 到本轮实验结束一字未动，
中间经过了 8 个实验进程与两次临时实例起停。实测证据在 §22：P1（空台账）192.4 秒 → **P2（重启进程、沿用 P1 写出的那 98 行）81.1 秒**，
比同进程第二发 B（73.2 秒）多的 8 秒是模型载入（C−B=7.3 秒对得上），**不是调优** ⇒ 重启不重付这笔账。

会让它不顶用的五件事：

1. **MIOpen / ROCm 版本变** —— 文件名带 `3_6_1_39d8d603`，换版本 = 换文件名 = 旧台账根本不被查。
2. **架构变** —— 键是 `gfx115128`（设备自报 `gfx1151`，db 名里多出的那段我没去查它是不是 CU 数）。换 GPU 就是另一本。
3. **用户 / home 不对** —— 它在 `$HOME/.config/miopen`。部署机上预热是 A 用户跑的、服务是 B 用户起的，B 看不到；
   容器没持久卷就等于永远空台账。
   （顺带：这台机上该目录与文件权限都是 `0777`，谁都能写 —— 多个服务共用一份时注意别互相盖。）
4. **环境变量把它指走或关掉** —— `MIOPEN_USER_DB_PATH`（本轮四臂就靠它隔离真台账）、`MIOPEN_DISABLE_CACHE`、
   `MIOPEN_DEBUG_DISABLE_USER_DB`、`MIOPEN_DEBUG_DISABLE_FIND_DB`。
   ⇒ **我自己埋的陷阱**：20.4 建议"把台账随发布带走、用 `MIOPEN_USER_DB_PATH` 指过去"，
   那个路径**必须选在重启后还在的地方**。指到 `/tmp` 下（我实验里就是这么干的，因为我要的就是临时）等于每次开机都从头调优。
5. **它没有过期时间**：`.time` 那个 15 字节文件里是 `349722612430399`，而当下 unix 时间是 `1793706139` 秒 ——
   不是同一套钟（那个值折算成 ≈4.05 天，像开机以来的单调纳秒），是"上次写过"的记账。
   库里也搜不到 expire / TTL 类旋钮（只有 `MIOPEN_ENABLE_LOGGING_DATE_TIME`、`MIOPEN_ENABLE_LOGGING_ELAPSED_TIME` 两个日志开关）。
   ⇒ 台账只会随新形状继续长大（一趟 1K 生产约 +98 行）。

## 22. §21 欠的那一发：同一句话跨四种制度 —— 冷 db 逐位相同，`FAST` 换图（54% 像素、最大通道差 185）（2026-11-03）

   ⇒ 于是这笔交易的重心变了：**花掉的是"逐位复现"，买回的是第一发省约 110~120 秒**。
   要不要花，得拿 22.1 那两张自己看过才算 —— 我在 20.4 里替你判成"别开"，那个判断建立在这个量级被我高估之上。

3. 冷 db 那两发（§21 的 A 197.3 与这里的 P1 192.4）同制度重复性约 5 秒 ⇒ "第一发贵 120 秒上下"是量级，不是偶发。

## 25. 第 3 档铺成能用的一档：先砍掉那个多余的 python 中间层

denvor 判过图（"可以接受"）之后要做的是 §24.4 留的那笔账：把在线那一档的固定开销收回去，再铺界面。
量完发现**最大的单笔根本不是"要不要常驻服务"**。

### 25.1 桥那 10.2 秒到底花在哪（分段计时）

`dump_hidden` 自己打 lap（warm 盘、§24 那对输入字节）：

| 段 | 秒 | 能不能免 |
|---|---|---|
| C++：模型 + mmproj 载入 | **1.23** | 要常驻 C++ 进程才免 |
| C++：context 建立 | 0.21 | 同上 |
| C++：读图 + tokenize | 0.04 | 免不掉 |
| C++：五段 eval | **5.19** | 免不掉（真活） |
| C++：收割向量 | 0.12 | 免不掉 |
| 写 post.bin + pre.bin（90 MB）+ meta | ≈ 0.45 | post.bin 那 45 MB 直接不写 |
| **二进制合计** | **7.34** | |
| python 侧：起解释器 + `import torch` 0.7 + `import comfy.text_encoders.qwen_image21` 1.3 | **≈ 2.4** | **当场就能免** |

⇒ 节点本来就跑在 ComfyUI 进程里，torch 和模板都是现成的，§24 那条路却是
ComfyUI → **再起一个 python**（把它自己 import 过的那套再 import 一遍）→ 再 C++ 子进程 → 再把 45 MB 读回来。
那 2.4 秒与 GPU 一点关系都没有。常驻服务只能收掉 1.44 秒（载模型 + 建 context），先把这 2.4 秒拿了再说。

### 25.2 改法与逐位回归

新两层：`tools/llama_gate/gate_client.py`（`resolve_gate_bin` / `gate_layout` / `run_gate` / `cond_from_meta`）与
`tools/llama_gate/prompt_build.py`（`media_prompt`，不 import torch，好让 CLI 与节点共用一份）。
`encode.py` 退回成纯 CLI（§19/§23/§24 那些判读还是它跑出来的，留着复现）。二进制加 `--no-post`；
产物位置从 `/tmp/llama-gate/` 挪进 `tools/llama_gate/bin/`（已 gitignore）—— 那是**手编的补丁版 llama.cpp 产物**，
落 /tmp 等于每次重启都要重编一遍，而节点只会报"没有那个文件"。

三道逐位回归，全过：

1. 重编的二进制加 `--no-post`，在同一对输入上写出的 `pre.bin` 与旧的 45 MB **逐字节相同**，`meta.json` 相同。
   （`--no-post` 在墙钟上量不出好处：7.34 → 7.45 秒，噪声内。它省的是那 45 MB 的落盘 + 读回与页缓存污染，不是秒。）
2. 新的 `cond_from_meta`（`np.memmap` 按行取）与 §24 那份 `cond.pt` 最大绝对差 **0.0**。
3. 端到端腿见下面 25.3。

`gate_layout(meta, byte_size)` 是这次新加的对账，两道都盯着"拿到的是条件张量而不是崩溃"那种坏法：
`total_rows` 与 chunks 段长合计不符 ⇒ 那份 meta 不是这次取的（指错目录 / 被并发覆盖）；
字节数不够 ⇒ 二进制中途死了，后半截行是 0，DiT 照样跑完、出一张莫名其妙的图。

### 25.3 验收：改法不动像素

同一句指令、同一颗 seed、同一对输入字节，唯一变量是"切行这活儿在哪个进程里干"：

| 腿 | 墙钟 | 与 §24 的 C-live |
|---|---|---|
| D-inproc #1 | **64.5 秒** | **像素逐位相同**（最大通道差 0） |
| D-inproc #2 | **64.8 秒** | 同上 |

两腿的 png 文件 sha 与 C-live 不同（`a94fff…` vs `e545cbb…`）但像素相同 —— 差的是 ComfyUI 嵌在 PNG `tEXt`

三件事：

1. **冷启动 52 秒不是远端带来的**，是 §13 那条"进程重启缓存清零"：DiT 重新载入、节点输出缓存空的。
   §25.7 在 1K 上量到过同一件事（66.3 vs 64.5），这是 720p 第 3 档的版本。
2. **远端没有任何额外开销**：稳态 25.35 与 §25.4 的本机 25.4 对得上。服务端就是本机那台 ComfyUI，
   网络只传几十 KB 的图（浏览器压缩后的人像+衣服）。
3. **重启后第一发贵**对第 3 档同样成立：重启后先自己跑一发预热，别让第一个真实用户撞上。
   （和 §15/§20 的 MIOpen"四档各打一发"不是一回事：那个是磁盘缓存、重启不丢。）

## 26. 内核 7.2.15 vs 7.3.3：出图速度没有可测量的差异（2026-11-09）

### 26.1 起因

denvor 把内核从 7.2.6 升到 7.3.3（11-09 17:40 装、17:42 启动）问"是不是快了"，后来又切回 7.2.15，
于是有了同一台机、同一套代码、**两代内核各测一遍**的机会。

amdgpu 是**内核自带模块**（`/lib/modules/<ver>/kernel/drivers/gpu/drm/amd/amdgpu/amdgpu.ko.zst`），
`/opt/rocm` 用户态没动 —— 所以这一换确实换了 GPU 驱动，值得量。

先把变量钉住，全是"没变"：

| 项 | 状态 |
|---|---|
| ComfyUI | HEAD `17ff1dcc`（11-01） |
| PyTorch / ROCm | `2.14.0+rocm10.1.0` / `(7,16)` —— 11-03、11-04、11-08、11-09 四次启动日志逐字相同 |
| 自定义节点 | `qwen21_posonly_encode.py`（11-02）、`qwen21_precomp_cond.py`（11-03） |
| 权重 | 未变 |
| MIOpen 缓存 | `~/.cache/miopen/3.6.1.39d8d603/gfx1151_20.ukdb`（11-03，208 KB），跨内核升级存活 |

### 26.2 两代对照（全量，服务端 `Prompt executed`）

每发**换不同的衣服图**（保证编码缓存失效，见 §26.3），多发放取平均：

| 档 | 7.2.15 各发 | 均值 | 7.3.3 各发 | 均值 | 差 |
|---|---|---|---|---|---|
| 480p | 10.77 / 10.82 / 11.07 / 10.95 | **10.90** | 10.83 / 10.80 / 10.89 | **10.84** | −0.6% |
| 720p | 25.93 / 25.15 / 24.81 / 24.68 | **25.14** | 24.36 / 25.76 / 25.41 / 25.06 | **25.15** | +0.04% |
| 1K | 64.24 / 63.28 | **63.76** | 62.83 / 63.34 / 62.36 | **62.84** | −1.5% |

三档的均值差都在 **1.5% 以内**，而发间波动本身就有 ±3%（720p 7.2.15 是 24.68~25.93）。
720p 的均值只差 **0.01 秒**。冷启动也对得上：7.2.15 **46.04** 秒、7.3.3 **45.91** 秒。

**结论：内核 7.2.15 → 7.3.3 对出图速度没有可测量的影响。**

### 26.3 两个口径坑（这次各栽了一下）

1. **"同图同 prompt、只换 seed"的第二发会整个跳过编码节点。**
   编码节点的输入是 clip / vae / prompt / resolution / 图，**不含 seed**（seed 是 KSampler 的输入）。
   所以换 seed 重跑时 ComfyUI 直接复用编码产物，量到的只是采样段：720p **全量 25.15 秒 vs 只跑采样 19.21 秒**，差 6 秒。
   我第一轮就是拿 19.21 去比基线 25.35，差点报成"快了 25%"。
   **要量全量，两发必须换图或换 prompt。**

2. **这个缓存会被"跨档位穿插"挤掉。**
   上面那条成立的前提是缓存还在。7.3.3 那次连跑六发 720p，缓存保住了，量到 19.21 秒；
   这次 7.2.15 上把 480p / 720p / 1K 穿插着跑，几个"同图换 seed"的发次**一个都没命中**
   （480p 10.95、720p 24.68、1K 79.82，全是全量）。
   ⇒ 任何"跑一发别的再回来"的测量，量到的都是全量。这条正好解释了 §25.4 那句"同会话交替有互相挤显存的嫌疑"。

3. **切换档位后第一发有惩罚**（7.3.3 上量的）：720p 切到 480p 再切回，第一发 **24.85 秒**、第二发 **19.17 秒**。
   和上一条是一对：都是"缓存里没有这一档"的代价。

### 26.4 基线 25.35 秒是全量，两代采样速度一字不差

查 11-05 的日志：14:34:06 入队、14:34:11 起采样、14:34:31 完成 ⇒ 采样段 **20.0 秒**、编码段 5 秒，合计 25.35。
而 7.3.3 的采样段是 **19.21 秒**（9 发均值）。**两代的采样速度一字不差** —— 这是"内核没影响"最硬的一条证据。

### 26.5 为什么没差异：那个提升是 7.4 的，而且本机 IOMMU 已关

denvor 的直觉有出处，但**版本记错了**：

- **18~23% 的 AI/LLM 提升是 Linux 7.4 的 AMD PerfOpt**（Phoronix 2026-09-29 / 10-30），
  机制是**让 iGPU 绕过 IOMMU 直接访问系统内存** —— 统一内存架构下 GPU 访问内存要过 SoC IOMMU 做页表翻译，这就是瓶颈。
  7.4 还没发布（10-31 是 `7.4-rc2`，预计 12 月下旬）。
- **7.3 的显存改进是另一回事**：dmemcg（Device Memory Control），HN 那帖标题直接是
  *"Linux 7.3 improves performance when running out of vRAM"* —— 是**显存不足时**的驱逐/优先级管理。
  本机 131 GB 统一内存根本不超订，触发不到。
- **本机内核 cmdline 里已经 `amd_iommu=off`**，`/sys/kernel/iommu_groups/` 是空的（0 组）——
  **PerfOpt 干的事我们早就手动做了**。AMD 那边对 Strix Halo 单机的建议原话也是
  "just disable IOMMU and skip it all together"。

⇒ 实测 7.2.15 ≈ 7.3.3 完全符合预期；**升 7.4 对这台机器也不会有额外提升**（IOMMU 已经关了）。
那 18~23% 是给 IOMMU 开着的人的。

**这条的前提会过期**：哪天 cmdline 里的 `amd_iommu=off` 被去掉了，7.4 的 PerfOpt 才会值钱。

## 27. 取数改成常驻服务：逐位回归与性能（2026-11-10）

### 27.1 为什么做

§25.5 判过"常驻服务不划算"（1.44 秒占 1K 的 2%），但那是**单次视角**。实际用量是**几百次/天**
（用户点 + 后台批量），300 次 × 1.9 秒 ≈ 每天 10 分钟。

**所以 §25.5 那句判断要加个前提：只在低频率下成立。**

### 27.2 做了什么

- `dump_hidden.cpp`（CLI）→ `llama_gate.cpp`（常驻服务）：读配置 → 载模型一次 → 监听 Unix socket
  → 循环（收图 + prompt → 逐 chunk eval → 切行 → 回张量）
- 客户端（节点、`encode.py`）改走 socket，不再起子进程、不再读写 `pre.bin`
- systemd 管（`llama-gate.service`，`User=denvor`，`RuntimeDirectory=llama-gate`）
- 协议是自建的（`tools/llama_gate/protocol.py`）：`magic | version | flags | 图数 | [图长+图字节]… | prompt长+prompt`
  → `magic | status | 行数 | n_embd | slots数 | [slot]… | 张量`；`status != 0` 时带一句人话
- 切行（`keep_rows` 那套）搬进 C++，只回 115 行 / 1.9 MB（不再回 45 MB）
- `llama_ready` 的语义从"二进制文件在不在"改成"**服务连不连得上**"

### 27.3 逐位回归：全过

| 对照 | 结果 |
|---|---|
| 服务端切行 vs Python `keep_rows` + `cond_from_meta` | **逐位相同**（最大绝对差 0.0，115 行、slots `[8,14]`） |
| 端到端出图（`cond_path` 注入基准 vs 现场取数） | **逐位相同**（≥1 占比 0.0%、平均通道差 0.0） |
| 服务重启后再跑 | **逐位相同** |

### 27.4 性能：比预估多省 4 秒

720p 第 3 档，连跑 5 发（每发换不同的衣服图，避开编码缓存）：

| | 各发（服务端 `Prompt executed`） | 均值 |
|---|---|---|
| 改造前（§26.2，7.3.3 那组） | 24.36 / 25.76 / 25.41 / 25.06 | **25.15** |
| 改造后 | 19.14 / 19.01 / 19.11 / 19.04（第一发 23.07 是切换后首发，不算） | **19.08** |

**省 6.07 秒（−24%）**，比设计里估的 1.9 秒多 —— 多出来的是"起子进程 + 写 45 MB 盘 + 节点读盘"
这些原来没单独计的量。

### 27.5 换模型：本机验不了

设计里说要验"改 `LLAMA_GATE_GGUF` + 重启能切"，但本机只有这一颗 Qwen3-VL 的 gguf，
所以改成验"重启后仍能工作"（已通过，见 27.3）。真换模型时留意 `LLAMA_GATE_N_BATCH`：
它必须 ≥ 单个 chunk 的 token 数（`llama_gate.cpp` 头注释第 2 条），写死会**静默出错**。

### 27.6 一个坑：基准的输入图被换过

存基准时记的 `inputs.sha256` 是 `42214a2e…`（1152×1536），而 repo 里 `data/llama-gate/img1.png`
现在是 `58d1ae81…`（736×992）—— 不是同一张。

差点因此误判成"服务与 CLI 的数值路径不同"：服务是自洽的（重启后两次逐位相同），
与基准的差异**全在输入图**。用同一张图再比，逐位相同。

⇒ 记基准要连**输入图**一起记（sha256 + 尺寸），只记 prompt 和 seed 不够 —— 这是 §24.2/§24.3
那条"输入字节不同 → 成图有 0.098% 的 >16 像素差"的同一件事，只是这次发生在条件张量上。
