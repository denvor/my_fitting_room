# 虚拟试穿工具 · 设计文档

日期：2026-10-26　状态：待评审

## 1. 意图与动机

做一个只给自己用的本地网页工具：上传一张本人照片和一张衣服照片，调用千问 `qwen-image-3.0-pro`，
生成"本人穿着这件衣服"的图。目的是省掉开 ComfyUI、装模型、拼工作流的麻烦——只想在浏览器里
传两张图、等一分钟、看到结果，并且过几天还能翻回来看。

衣服的细节和这个人本身，同等重要，都是及格线。做出来的图如果脸变了、或者衣服被模型"重新设计"
了款式颜色，哪怕画面再漂亮也算失败。这条约束是本项目的核心，提示词和验收标准都由它决定。

## 2. 目标

- 两个上传框（本人照片、衣服照片）+ 一个"开始试穿"按钮，一次一件衣服。
- 一次生成 1 张图。不满意就点"再来一次"，复用页面上已有的两张图，换随机种子重新生成，不必重新上传。
- 等待期间有可见的进度反馈（详见 5.3），同一时间只允许一个任务在跑，跑的时候按钮置灰。
- 一个图库：每条记录展示人像、衣服、成品三张图，附生成时间与消耗数字；能点开看大图。
- 图库里的记录可以删除，删掉就是连人带图从磁盘移除。
- 每次生成的消耗数字（接口回传的 `usage`）显示在结果上，让人看得出额度是怎么掉的。
- 所有图片落到本地磁盘，图库离线可看，不依赖接口那条 24 小时就失效的链接。

## 3. 非目标

- 不做账号、登录、多用户、并发排队。
- 不做提示词输入框（评审时明确否掉：页面保持"两个上传框 + 一个按钮"）。
- 不做一次多件衣服、上下装组合试穿。
- 不做 1K/2K 分辨率开关，固定 1K 档。
- 不做图片编辑类功能（换背景、修脸、局部重绘等），只服务"把这件衣服穿上"这一件事。
- 不做云端部署、不做鉴权和访问控制（使用者明确要求绑 `0.0.0.0` 以便局域网调试，接受因此被同网段访问）。
- 不做图库内的"按这条记录重新生成"（数据都存着，将来要加是独立小改动）。

## 4. 反目标（技术上跑通但项目失败的样子）

- 人脸变形、身份不符，或者衣服款式/颜色被模型改掉。
- 本人照片被转发到除千问接口以外的任何第三方。
- 等待的一分钟里页面看起来像死掉了，让人以为失败而反复刷新。
- 结果只在页面上存在几分钟，回头就找不到（这条由图库解决）。

## 5. 已定的怎么做（评审中一条一条定下来的）

### 5.1 界面
单页，两块上传区（本人照片 / 衣服照片），一个按钮，一个结果区，一个图库区。没有参数面板，没有文本输入框。

### 5.2 一次一张，靠重试
接口支持一次出 1–6 张（`n` 参数），但定为每次出 1 张：实测同图同提示词、不同种子连跑两次都成立，
说明单次成功率够用，不必为挑图多付一倍的等待和额度。"再来一次"就是重新发一次请求。

### 5.3 进度条是估的，不是真进度
接口是同步的一发请求，中途没有任何进度可查，真进度条做不出来。定为：按实测耗时估一条会爬升的进度条，
接近末尾时放慢，结果一到立刻填满；同时把已经等了的真实秒数用数字打在旁边（例：`生成中 · 43 秒`），
估算归估算、事实归事实。

### 5.4 固定提示词
提示词写死在后端，中文模板，内容包含四件事：说明图像1 是本人照片、图像2 是衣服照片；要求保持图像1
人物的脸部五官、发型、身材、姿势、背景不变；要求完整还原图像2 衣服的款式、颜色、纽扣、口袋、走线、
面料纹理；要求忽略衣服照片里的衣架、背景和其他衣物。用户不给任何修改入口。

### 5.5 同一时间只有一个任务
服务端不做任务表、不做队列、不做轮询。进行中再点无效。重试所需的两张图由浏览器自己留着，
服务端不保存会话状态。

## 6. 接口事实（实测与官方文档，写代码时照此为准）

### 6.1 调用方式：已实测跑通
```
POST https://token-plan.maas.qianwenaiapi.com/api/v1/services/aigc/multimodal-generation/generation
Authorization: Bearer <.env 的 API_KEY>
Content-Type: application/json
```
域名从 `.env` 的 `OPENAI_URL` 推导：去掉结尾的 `/compatible-mode/v1` 再接 `/api/v1/...`。
模型名取 `.env` 的 `MODEL`（`qwen-image-3.0-pro`）。注意 token plan 的地址和 key 与文档里的
`maas.qianwenaiapi.com` 示例不同，以 `.env` 为准。

请求体：`input.messages` 只放一条 `role: user`，`content` 数组按顺序为
`{image: 人像}` `{image: 衣服}` `{text: 提示词}`，有且只有一条 text。
`parameters` 用 `{"n": 1, "size": "宽*高", "watermark": false}`。
`prompt_extend`（默认开）与 `enable_thinking`（默认开）保持默认——实测对质量有用，代价是耗时。

响应：`output.choices[0].message.content[*].image` 是结果图 URL（PNG，**24 小时过期**）；
`usage` 里有 `input_image_count`、`output_image_count`、`input_image_type`、`output_image_type`、
`output_width`、`output_height`；`output.rewrite_status` 表示提示词是否被改写。失败时返回非 200，
带 `code` 和 `message`（例：`InvalidParameter` / `Failed to download image URL after retries.`）。

### 6.2 图片必须用 base64，不能用 URL
实测传外网图片 URL 会被服务端拒绝（`Failed to download image URL after retries.`，0.2 秒即返回）。
所以用户本地上传的图一律转成 `data:image/jpeg;base64,...` 内嵌进请求。

### 6.3 输入限制与处理
支持 JPG/JPEG/PNG/BMP/TIFF/WEBP/GIF（仅第一帧）；单图 ≤10MB；宽高 1–8000 像素（官方建议 384–2048）；
长宽比 ≤10:1。因此上传后需要：按 EXIF 修正方向、长边缩到 ≤1536、转成 JPEG 再内嵌。
（选图后浏览器已经先压到长边 1536 并把方向定死，省掉手机上行那几 MB；服务端这套照常跑，
当浏览器不配合时的兜底，两边算出来的尺寸一致。）
多图时**输出宽高比默认由最后一张图决定**，所以必须显式传 `size`，取值按人像图的比例算，
把总像素控制在 1K 档（面积 ≤2,250,000，且不低于 512×512）。

### 6.4 耗时（实测，1 张、默认开启改写与思考）
- 1K 档（896×1152）：**55.8 秒**
- 2K 档（1792×2320）：**121.8 秒**

耗时随负载波动很大，复测同一对样例图又见到 46 / 48 / 51 / 103 秒，还有一次 300 秒读超时
（`The read operation timed out`）：客户端放弃了，服务端还在跑，额度迟到 8 分钟照样扣走 58。
所以实现里的等待上限是 600 秒（`GENERATION_TIMEOUT`）—— 300 秒不是余量，是正好站在长尾里。

### 6.5 限流与计价口径
每分钟最多 5 次请求、10 并发、异步队列 200。计费按像素面积分档：面积 ≤2,250,000 记 1K 档，
更大记 2K 档。**实测：token plan 里一次成功的 1K 生成扣 58 credit，2K（1792×2320）一发 108 credit**
—— 不是两倍关系，2K 摊到每像素更便宜；而且请求 2K 时连输入都被划进高档
（`input_image_type` 从 `qima_input_1k` 变成 `qima_input_2k`）。换算由 `qianwen subscription status` 的 `individual.monthlyCredits` 得出
（连跑三次 1K 都是 58.000，纯等待和状态查询均为 0.000）。界面把接口回传的 `usage` 原样显示出来，
另外用 `剩余 credit ÷ 58` 在页眉报一个"还能试穿多少次"——这是 1K 档的换算值，不是万能次数。

### 6.6 效果基线（已验证的最低质量线）
用官方示例的一对图（896×1152 侧脸低头人像 + 挂着的浅蓝牛仔衬衫）实测：人像的脸、发型、姿势、
灰绿棚拍背景全部保留；衬衫的水洗蓝色、单胸袋位置（穿者左胸）、白色纽扣、面料织纹正确；
衣服图左侧露出的半件黑色衬衫被正确忽略。1K 与 2K 两发都成立。新写的提示词模板只要偏离这个
效果，就算不合格。

## 7. 交给实现者自己定的部分

以下是我的判断，不是使用者提的，改了不用回头问，但改错了要能看出来：

- **技术栈**：Python + Flask（开发服务器开多线程即可，长请求不阻塞图库页面）+ Pillow（EXIF 矫正、
  缩放、缩略图）；HTTP 请求用标准库，不额外引入 requests。前端一个 HTML + 原生 JS + 手写 CSS，
  不引入构建工具和框架。虚拟环境用项目已有的 `.venv`（Python 3.13，目前是空的）。
- **监听 `0.0.0.0:8000`**：使用者要在局域网里访问（很可能用手机打开页面、直接用手机相册上传来试手感），
  所以绑所有网卡、不加鉴权，端口 8000。
- **存储布局**：`data/records/<时间戳>/` 下一个目录一条记录，放 `person.jpg`、`garment.jpg`、
  `result.png` 和 `meta.json`（时间、提示词、size、`usage`、`request_id`、耗时）。图库扫目录读，
  不用数据库。缩略图在生成记录时一并产出。
- **失败处理**：把接口的 `code`、`message`、`request_id` 原样显示在结果区，不写自定义错误话术；
  请求失败时页面上两张图还在，直接点重试。
- **上传即校验**：不是图片、超 10MB、缩到长边 1536 后仍小于 384 像素、或长宽比超 10:1 → 直接拒绝并说明原因。
- **进度条估算基准**：55 秒（实测 1K 耗时）。
- **失败的生成不进图库**：只在结果区显示接口原话，输入的两张图留在页面上，直接点重试。图库只收成功的记录。
- **不做"取消"按钮**：请求一旦发出，服务端那边就已经开始算额度了，前端中断请求也拦不住它。
  给一个取消不掉什么的按钮比不给更容易误导人。等待期间页面其余部分照常可点，图库能翻。
- **验收用的示例图入库**：第 6.6 节那对图（人像 + 衬衫）保留在 `samples/` 目录，
  验收和以后改提示词时直接拿它跑对照，不用每次去外网下载（这台机器上 GitHub 不稳，实测下载会断在半截）。
- **`data/` 加进 `.gitignore`**：图库里全是你自己的照片，绝不进版本库（对齐第 4 节反目标）。
  `samples/` 是官方示例图，可以入库。
- **两条缩放规则打架时，面积优先**：6.3 的"长边 ≤1536"和"总像素 ≤2,250,000"对接近正方形的人像图
  会冲突（1536×1536 = 2.36M，会被算成 2K 档，慢一倍也贵一倍）。定为：**以人像图的宽高比为基准，
  把总像素缩放到不超过 2,250,000 的最大档**，长边因此自然落在 1536 以内。宽高都取 8 的倍数。
- **生成成功但结果图下载失败**（已扣额度、图没拿到）：自动重试下载 3 次；仍失败就把接口给的原 URL
  显示在结果区并说明它 24 小时内有效，你可以自己另存，不要让它无声无息地丢掉。这条记录**不落盘**。
- **删除的交互**：删除入口放在大图查看层，一个"删除这条"按钮，点击后用浏览器原生确认框二次确认，
  确认后把整个记录目录删掉。不做回收站、不做多选批量删。
- **服务端要挡住第二个请求**：5.5 说的"同一时间只有一个任务"要在服务端落地，一个进程内布尔锁就够
  （不是任务表）：正在生成时的新请求直接返回"上一次还在跑"，防止开两个标签页重复扣额度。

## 8. 验收标准

1. `.venv/bin/python app.py` 起服务，监听 `0.0.0.0:8000`；本机 `http://127.0.0.1:8000` 能看到页面，
   同一局域网内的另一台设备用本机 IP 访问 `:8000` 也能打开。
2. 用第 6.6 节那对示例图走一遍（真实调用接口，跑 1 次）：出图达到该节描述的质量线（脸、姿势、背景不变，
   衬衫细节还原，忽略旁边的黑衬衫）。这一条必须真实调用接口跑出来，不能只靠读代码判定通过。
   **验收只到官方示例图为止**：使用者明确不同意拿本人照片进来测，所以"换成真实自拍还保不保得住"
   这条风险不在验收范围内，留到日常使用里自己观察，不满意再回来改 5.4 的提示词模板。
3. 生成过程中进度条爬升、秒数在走，结果返回时立刻填满。
4. 结果落到磁盘，重启服务后图库仍能翻到这条记录，缩略图点开能看大图。
5. 出图后点"再来一次"，不需要重新上传，能出第二张不同的结果。
6. 关掉网络或写错 key 的情况下，页面显示接口原始错误信息，不白屏、不卡死。
7. 全程没有任何请求发往千问接口以外的域名（结果图从接口给的 URL 下载，属于同一条链路）。
8. 图库里删掉一条记录（确认后），页面不再显示它，`data/records/` 下对应目录也确实不存在了。
