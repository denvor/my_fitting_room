# 本机 ComfyUI 这一路动过什么：从 146 秒到 64.5 秒

这份是**汇总与判断**，不是测量记录。数全部在 `docs/comfyui-measurements.md`（下面写 §N 就是那一节，可点回去核）；
这份只回答三件事：**动了什么、值多少秒、这次动它该不该动**。

范围：2026-10-31 ~ 11-03 三天，本机 AMD Radeon 8060S（gfx1151，124 GiB 可分配显存）+ ComfyUI 0.39.0 → 0.43.0，
另一台 RTX 5060 Ti 16GB 作为对照机出现（它的结论不能搬回本机，见"跨机器"那一节）。
同一件事的**叙事版**（不按结果表排、按"怎么走到那一步"排，对外可读）在 `docs/article-tuning-comfyui-with-ai.md`。

## 判据（我按这三条分类，不是只问"有没有变快"）

- **必要** —— 不改就不能出图，或者**改了才对**（不是快了，是不再静默出错）。这种不看秒数。
- **划算** —— 有实测增益，而且没拿画质或逐位复现去换。
- **不划算** —— 量下来省 0~2 秒；或者省的是**我自己造出来的**开销；或者要用"同 seed 同一张图"去换。

"不划算"不等于"白做"：下面每一条不划算的都换来了一句判据，我把买它的成本一并写在旁边。

## 一、上车的（今天还在生产里跑）

| # | 动的是什么 | 形态 | 实测 | 判 | 代价 |
|---|---|---|---|---|---|

| 6 | 二进制加 `--no-post`（不写那 45 MB `post.bin`） | 一个命令行开关 | 墙钟**噪声内**（7.34 → 7.45 秒）。省的是磁盘与页缓存污染 | 别记成功劳 —— 它的价值是"别写没人读的东西" | 无 |

**一条不是我们的改动、但必须留着的证据**：§8 量到 `QwenImage21Cache` 的 prefix 缓存**值 1.88 倍采样时间**（1K 每请求 48.5 秒、占整次 33%），
而且**缓存是精确的**（`gpu` 与 `off` 出图逐位相同）。所以那面"官方默认就开着"的旗别手痒去关；
而"让它跨请求不重置"最多再值 **6.9 秒**，只有第 2 行那 44.4 秒的六分之一 —— 这句话当年替我们排掉了一个假机会。

## 三、时间线：146 秒是怎么掉到 64.5 秒的（1K，同机同图同 seed）

```
146.0 ~ 146.3   基线（官方编码节点、cuDNN 关着）        §1：编码 89.4~89.6（61%）+ 采样/解码/存图 56.3（39%）
      │  −44~45 秒   §9  少编一遍负向                出图逐位相同 ✓
101.2 / 102.1
      │  −29 秒      §15 COMFYUI_ENABLE_MIOPEN=1     出图换了（63.489% / 平均 0.784）
 73.2 / 73.1
      │  −8.7 秒     §25 编码换 llama.cpp（第 3 档）   出图又换了（>16 占 0.330% / PSNR 38.40）
 64.5
```

**−56%（146 → 64.5），但复现性是递减的**：第一刀逐位相同，后两刀各换了一次图。
所以承诺要分开说：**保住逐位复现的那条链只到 73.2 秒**（第 2 档），再往下那 8.7 秒是**用逐位复现换的**；
而那个 8.7 是**下限** —— 64.5 那一发还含着新进程载权重，同为"新进程"的口径配对比是 −15.7 秒（§25.3、§24.4）。

其余档位（同一条链，但每一步不是都量过）：

| 档 | 基线（官方节点 + 关 cuDNN） | 去负向后 | 开 MIOpen | 第 3 档 |
|---|---|---|---|---|
| 480p | 26.0 / 26.1 / 26.2 秒（§6） | **没单测** | **11.2**（§15） | **11.8**（§25.4） |
| 720p | 66.4 ~ 67.3 秒（§1） | **44.4**（§9） | **29.1**（§15） | **25.4**（§25.4） |
| 1K | 146.0 ~ 146.3（§1） | **101.2**（§9） | **73.2**（§15） | **64.5**（§25.3） |
| 2K | 539.6（10-30）/ 543（10-31） | 拆不开 | 与上一行合计 **302.5**（§17） | 本机两条都选不到它 |

2K 那一行**故意不给倍数**：§17 明写"543 → 302.5（−44%）是**两次提速的合计**，拆开要在 2K 再跑一发官方节点，没跑，
别当 MIOpen 单独的功劳"。480p 也留了个洞（去负向那一刀在该档没单测）——**别拿 1K 的比例倒推它**。

## 四、这四次大改的来龙去脉

上面那两张表是按"结果"排的。这一节按"怎么走到那一步"排 —— 因为这四次里没有一次是"想到要优化"直接优化出来的，
每次都是**上一轮的数把下一步逼出来的**。

### 4.1 那 44 秒没人读的负向（§8 → §9）

**起因不是"想快"，是"想移植"**。§1 量到编码占 146 秒的 61%，于是问题变成：这块肉是"喂给模型的图太大"还是"引擎不行"？
要回答就得知道编码段里每一段花在哪。做法是给 ComfyUI 的四个函数临时插计时、另起一个 8189 实例跑
（生产那台 8188 全程不重启，因为 Python 已经把原文件 import 进去了），探针自带 `cuda.synchronize()`，
不然量到的只是提交时间；测完 `git checkout --` 撤干净。

拆开之后跳出来两件事（§8）：

- 我们传的 `negative_prompt` 是**空串**，节点照样把两张参考图**又过一遍视觉塔**（31.9 秒）再走一遍 8B（12.5 秒）。
  负向那一整趟 **44.4 秒 = 一次 1K 请求的 31%**，而 cfg 1.0 下采样器永远不用它。
- 视觉塔算完就被扔：`cond_before=2865 → dropped=2750`，真正进 DiT 的只有 **115 个 token**。

第一条当时看着无解：**正负两次编码在同一个节点里**，图上怎么接线都改不了 —— 这条决定了只能改代码，
于是有了那个 fork 出去的节点。第二条则埋了后面的伏笔：既然 2736 个 token 白算，能不能干脆少喂点？
这条走了很远（4.3 与 4.5）。

**验收方式是这件事最幸运的地方**：只换 `class_type`，同 seed 出图**逐位相同**（差异像素 0.000%、单像素最大差 0）。
"省了 44 秒而图一张像素都没动"这种承诺，只有逐位相同才敢写。反手就被 §12 教会：**这条标准不能跨后端用**。

### 4.2 一行环境变量，是从"要不要写个 C++ 桥"那个问题里掉出来的（§13 → §14 → §15）

§13 接 §8 那条"2736 个 token 白算"往下推：唯一剩下的结构性大肉是**视觉塔吃多大**。
它同时给出两个便宜的结论 —— 重试本来就免费（同图同指令只换 seed，101.0 → 54.8 秒，**−46%**，
因为 ComfyUI 的上传接口对同内容不改名、缓存 key 不变），以及"`resolution` 这一个数同时管着三件事"
（视觉塔的像素、`reference_latents`、输出尺寸），所以"少喂像素"没有现成旋钮可拧。

于是 §14 换了个思路：**能不能整个换掉这颗文本编码器的执行引擎**。在同一颗 APU 上用 llama.cpp 跑同一批 vision token，
量到 **1.12 vs 11.93 ms/token ≈ 10.6 倍**，而且两边对得上账（grid 96×72 → 合并 1728 token 完全一致）。
当时的判断写得很硬：那 10 倍是实现差距，不是算法差距也不是硬件差距 —— 听起来够理由开一个大工程
（自己编译 llama.cpp + 写调用程序 + 新节点 + 评图）。

**真正把这件事拦下来的不是判断，是那句刹车**：既然 10 倍是 kernel 差距，ComfyUI 侧也可能有就地修法，
先查这个再做移植，工作量差一个量级。§15 就是那次"先查"，做法是 op 级剖析（真权重、真 ops、逐叶子模块计时）：

- 一趟编码 46.61 秒里，**`Conv3d (patch_embed)` 两次调用共 25.98 秒 = 55.7%**；视觉塔那 27 层的 Linear **全部加起来才 1.01 秒**。
- 那个卷积在数学上就是个矩阵乘（kernel 与 stride 都是 `(2,16,16)`，无重叠）：**Conv3d 16538 毫秒 vs GEMM 0.80 毫秒**。
- 两次假信号差点把线掐掉：replica 多 `permute` 了一次（喂进去是被压扁的破图）、ComfyUI 的 `reset_parameters()` 返回 None
  （随机建出来的权重是未初始化的垃圾位）。都靠"真权重 + 真形状"那一版才立住。
- **进程级二分**定死：同一个 Conv3d，只 `import torch` 时 0.70 毫秒，**一旦 `import comfy.model_management` 就变 16538 毫秒**。
  那就去读那个模块 —— `comfy/model_management.py:486-490`：AMD 上除非 `COMFYUI_ENABLE_MIOPEN=1`，
  ComfyUI 设 `torch.backends.cudnn.enabled = False`，注释写着 *"Seems to improve things a lot on AMD"*。

**结果：那 10 倍里有 26 秒是它自缚手脚。** llama.cpp 只是不受这个开关影响。移植的动机当场从 −36% 掉到 −10%~−15%。
复盘一句：这个开关是 ComfyUI 针对 AMD 的**默认行为**，看起来像"官方为 A 卡调过"，所以没人觉得它奇怪 ——
把它揪出来的不是"想到要优化"，是**先按 op 拆一遍、再决定要不要动手**那个次序。

### 4.3 那 8.7 秒绕了三个来回才拿到（§18 → §19 → §23 → §25）

§15 之后移植看起来死了，但 §14 里还挂着一句更根本的：**能不能拿到 llama.cpp 的 pre-norm 出口**。
因为 §5 钉过 conditioning 取的是"最后一层 hidden state 且**不加最终 RMSNorm**"，而 llama.cpp 的默认出口已经过了 norm。
这是生死线，比速度先。于是 §18 做判死实验：分词那一关过了（117 token 逐位相同），
但带图那格量出余弦只有 **0.687**。当时据此判"不做"，理由三条，其中一条是诚实的：
**那个读数连"差在实现还是差在权重"都分不开，在分不开的前提下动手等于把工程押在没测准的数上。**

第二天（§19）把这一格做穿了，结论是**作废**：0.687 是**我自己把行号坐标系用错**
（`image_spans` 是丢掉 system turn **之前**的完整序列坐标，拿去切已经丢过头的张量就整块错 14 行）。
补上 pre-norm 出口（本地补丁 +15 行，且 HTTP 那条口拿不到，必须自己编译）之后逐位置重测：
**0.98247 / 0.98080**，"图像进去之后不是同一份条件"那句收回。同时收益也订正：先前推算的 −10% 是低估，
量下来是 **−19%**。

然后卡在一件**数判不了**的事上：0.982 是 19% L2 的条件扰动，而 §15 那次只换个卷积实现（扰动小一个量级）
都已经有 63% 像素不同 —— 所以"会不会画出一张看得出不一样的图"只能生成出来给人看。
§23 注进生产图打了一发，§24 把它接成在线取数，**denvor 看过图判"可以接受"（2026-11-03）**，这件事才继续往下走。
§25 最后收下那 8.7 秒（1K 73.2 → 64.5），过程中还查出 §23 那对对照是脏的（离线腿的条件从原始记录文件切、
生产输入过了 `prepare_upload` 的 JPEG 重编码 ⇒ 比的是"引擎 + 输入"两件事）。

这条链值钱的地方：**它三次改口都是被下一个测量逼的，不是被新想法逼的。**

### 4.4 用户给的两句 export，量出来一个是假的、一个是贵的（§20 → §21 → §22）

这一组起因最朴素：denvor 贴了两行想加的启动环境变量（`MIOPEN_FIND_MODE=FAST`、`MIOPEN_ENABLE_CACHE=1`）。

- 第二个**名字在库里不存在** —— 用 `strings` 直接问 libMioOpen.so，只有 `MIOPEN_DISABLE_CACHE`。
  设了不报错也没效果。这一条判死只花一条命令，**如果照着文档背就白背了**。
- 第一个是真的，但它只管"这台机没见过的卷积形状"：稳态一分钱不省。于是量了冷账 —— 端到端生产图，
  新进程 + 空 db **197.3 秒** vs 同进程第二发 **73.2 秒**，拆开是调优 116.8 秒 + 模型载入 7.3 秒
  ⇒ **冷 db 那一发贵 124.1 秒（2.7 倍）**，而 `GENERATION_TIMEOUT = 300`，只剩 1.5 倍余量。
  **预热不是讲究，是别让第一发撞超时线。**
- 而 `FAST` 换不换图？第一版答错了：§21 四腿**各带了不同的 prompt 后缀**（后缀是 §0 为计时准备的），
  加了后缀就是四份不同的条件，于是它们两两之间 49%~60% 的像素差**不说明任何事** ⇒ 整轮像素比对作废，
  重跑成"同一句话跨四种制度"（§22）。订正后的结论：**空 db 从头调优与攒了三天的真 db 出图逐位相同**，
  `FAST` 则换内核（54.104% 像素不同、`>16` 占 0.70%、PSNR 36.36，人眼看是"同一次试穿的另一个细节版本"，
  差别在垂着那只手的袖口卷起程度），而且**它不写 find-db**，开了等于此后所有新形状都停在启发式内核上。
- 处置（denvor 判）：**两条都不设**；预热保留（现在有价签了）；要省冷账又不想动数值口径，走"台账随发布带走 +
  `MIOPEN_USER_DB_PATH` 指在持久盘"。

### 4.5 attention 那一整轮：本机只值 1 秒，但买了两句后来反复用的话（§9b → §10 → §11 → §12）

§9 那把刀搬到对照机（RTX 5060 Ti）上量，**几乎不省**（1K 省 0.4 秒，§9b）。
同一天深夜把那台加上 `--use-ck-attention`，采样段 −10.7 秒、**−28%**（§10）。
回头补本机的基线：sage-int8 **反而慢 3.6 秒**（§11），SDPA(AOTriton) 与 ck 差 1.0 秒（§12）⇒
本机三档后端打平在 3.6 秒内，"装 flash-attn 会有肉"这个前提不成立（本机 SDPA 默认就是 fused flash-class kernel，
单算子不指定 3.20 ms vs 强制 FLASH 3.20 ms）。

这一轮花了四种后端、两台机器、十几发 GPU 时间和一份 flash-attn 装法备案，本机净收益 **1 秒**。
它买到的是两句判据，后面每一步都在用：

1. **换后端会换图**（`--use-ck-attention` 走的是 int8 量化 attention）⇒ "逐位相同"这种验收**不能跨后端用**；
2. **同一处改动的收益是机器相关的**（负向编码本机 −44 秒、那台 ≲1 秒；ck 那面旗本机 −1 秒、那台 −28%）
   ⇒ **上车判据不能跨机器搬**。这一条也解释了为什么 §2/§10 那几张跨机器倍数表被改了三次
   （2.7×→3.1×、5.5×→9.5×、1.5×→2.1×）—— 每一次都是新变量，不是硬件变了。

## 五、四笔自己造出来、又收回来的结论

这些一个都没进"提速"账 —— 它们全是**假账**，而且是同一族假账：方法错了，数看着却很像样。

- **"跨机器约 80% 像素不同"**（§3）：把三通道直方图里第 2、3 通道的零值桶（索引 256、512）当差值算了 ⇒
  **任何两张图都会白送 66.7%**。改成"每像素三通道取最大差"，跨机器其实是 66.56% / 平均差 1.06。
- **整轮 §21 的像素差作废**：四腿各带不同的 prompt 后缀（后缀是 §0 为**计时**准备的，不加就会整链重放）。
  加了后缀就是四句不同的话、四份不同的条件 ⇒ 它们两两之间 49%~60% 的像素差**不说明任何事**。
  重跑成"同一句话跨四种制度"才是 §22 那组结论。**判时间的话不能拿去判像素。**
- **"带图 0.687"作废**（§18 → §19）：行号坐标系用错（`image_spans` 是**丢掉 system turn 之前**的完整序列坐标，
  拿去切已经丢过头的张量就整块错 14 行）。补上 pre-norm 出口逐位置重测是 **0.98247 / 0.98080**。
  教训：**错位的条件是向量、不是崩溃** —— 它安静地给你一个像样的错数（§24 的 `keep_rows.py` 三道断言就是为它写的）。
- **§23 那对对照混进了第二个变量**（§24.2）：离线腿的条件是从**原始记录文件**切的，而生产输入过了
  `prepare_upload` 的 JPEG 重编码（人像平均差 0.94/255、最大 18）⇒ 比的是"引擎 + 输入"两件事。
  重出干净那对（`A-fork` vs `C-live`）之后**结论没变**（0.385% → 0.330%、PSNR 38.19 → 38.40），但方法上的账要记。
  这一条还买了一个标定：**光是那次重编码就能让成图有 0.098% 的像素通道差过 16**，是引擎那一改的三分之一
  —— 于是"细节级差异"有了地板，以后判"改 X 换不换图"必须先核对两边输入字节（§0 第六条）。

这四条在记录里都留了"作废 / 订正"的原话，不是我事后回想出来的 —— 这一节只收**当时真的量错过**的东西。
共同点很一致：**每一次都是拿"能跑完、数也合理"的错口径交卷**（像素差 80%、余弦 0.687、四腿两两差 50%），
所以这一路给自己补的口径全都长这个样子：**先问两边比的是不是同一件事，再问快了多少**。

## 六、跨机器：为什么这一路的数不能搬

同一处改动在两台机器上的收益差着量级，这是本份清单里最容易被误用的一条：

| 改动 | 本机 8060S | 5060 Ti 16GB | 读法 |
|---|---|---|---|
| 少编一遍负向（§9 / §9b） | **−44 秒** | **≲1 秒**（四对独立比较都是这量级） | 那台上第二遍编码几乎不要钱（机制**没验**，§9b 设计好判别实验没跑） |
| `--use-ck-attention`（§10 / §12） | **−1 秒** | **−10.7 秒（−28%）** | 同一对替换（SDPA→ck），幅度差近无穷倍，**没解释** |
| 编码段本身 | 89.4 秒 | 9.0 秒（**9.9 倍**，§2 当晚更正，原写 5.4） | 差距几乎全在编码，因为 qwen3vl 8B 是**纯带宽活儿** |

⇒ 判据：**"上车判据只在本机成立"**。换机器（或者部署到 `/www/webroot/mfr` 那台）之前，
第 2 行那种"省 44 秒"的承诺要重打一遍，不能搬。§2/§10 那几张跨机器倍数表本身被改了三次（2.7×→3.1×、
5.5×→9.5×、1.5×→2.1×），每一次都是**新变量**（当晚重测、加了旗）而不是硬件变了。

## 七、"必要"这个词，三天下来我的答案

真正称得上"必要"的改动只有三类，**没有一类是为了快**：

1. **图结构必须那么写，否则静默出错**：参考图要写成 `images.image_1` 这种**点号平铺键** —— 换成嵌套字典或数组，
   ComfyUI **不报错，只是把参考图丢掉**，于是输出 1024 正方形、人和衣服全凭编（规格文档 `docs/superpowers/specs/2026-10-27-comfyui-source-design.md` §6.3）；autogrow 的前缀还两套
   （`image0` 起自 0 vs `image_1` 起自 1）；指令里那句中文"图像2"**必须**与模板的槽序对齐（§5）；
   第三档必须**把 `CLIPLoader` 从图里删掉** —— 节点不消费它不等于它不进显存（§25）。
2. **装了才对**：fork 节点的 `get_node_list` 照抄官方返回注解 `-> list[type[io.BaseComfyNode]]`，
   而这个符号在 0.43 的 `comfy_api.latest` 里**不存在** ⇒ 模块在 custom_nodes 导入阶段就抛，
   ComfyUI 只打一行 `0.0 seconds: ...` 就继续启动，**界面上一切正常**（头两发都栽在这儿）。
   判据从此写死：`GET /object_info/<节点id>` 拿到 `{}` 就是没装上（§9）。
3. **平台的坑**：AMD 上 `cudnn.enabled=False` 那个默认（§15）。它不是"优化"，是把一条参考实现的路解掉。

而"提速"那几刀的共性也很清楚：**它们全都砍在编码段上**（§8 拆开：视觉塔 63.8 秒 = 71%、8B 主干 25.3 秒 = 28%、VAE 1.0 秒）。
采样段三天里几乎没动过（54.6 → 53.7 → 53.5），因为 8 步 turbo 那一段本来就没肉；
attention 后端那一整轮（§3、§10、§11、§12：四种后端、两台机器、十几发 GPU 时间、一份装法备案）**在本机只值 1 秒**
—— 这是本份清单里"研究成本高于收益"最大的一块，但它买到了两句后面反复用得着的话：
**换后端会换图（所以"逐位相同"不能跨后端当验收）**，以及**收益是机器相关的（所以判据不能搬）**。

## 八、部署那一侧的落地清单（按这一路的结论排）

| 动作 | 在不在场 | 说明 |
|---|---|---|
| `comfy_nodes/qwen21_posonly_encode.py` → `custom_nodes/` + **重启 ComfyUI** | **运行依赖**，缺了应用入队就收到 `missing_node_type` | 自定义节点只在启动时加载；README「装与起」也写了"换机器不会自动跟着走" |
| `export COMFYUI_ENABLE_MIOPEN=1` | `ComfyUI/start.sh` 一行 | 上线前**四档各打一发预热**（每档在替后面的用户付约 124 秒），2K 那发要按十分钟留时间 |
| 确认部署用户**能写** `~/.config/miopen/` | 未确认 | **这条是推断，没实测**：写不了就不是"少攒缓存"，
   而是每一发都重新调优（§21 冷 db 那一发 197.3 秒 ⇒ 等于每发都付 124 秒）。目标机上打一发看 db 行数涨不涨就能定 |

| `export MIOPEN_FIND_MODE=FAST` | **不设** | 免掉一次性首发钱，代价是永久丢掉逐位复现（§22） |

| find-db 随发布带走（90 KB 文本 + `MIOPEN_USER_DB_PATH`） | 可选 | 想省冷账又不想动数值口径的唯一一条路；**必须指在持久盘上**（§20.4/§20.5） |
