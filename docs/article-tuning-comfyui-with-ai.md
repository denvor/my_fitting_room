# 在 AI 的帮助下调优 ComfyUI

掌机型显卡 Radeon 8060S，128GB 统一内存，ComfyUI 0.43，qwen-image 2.1 的图像编辑工作流。出图 1152×1536 要 146 秒。

三天以后，同一台机器、同一张人像、同一件衣服：73 秒。再加一档（把文本编码器换成 llama.cpp 跑）：64.5 秒。

中间做的事不是"优化了三次"。实测记录写到第二十五节，真改了东西的只有四次，其中三次改口是被下一个数逼出来的，还有一次差点把整台机器的编码引擎换掉——那个工程最后没做，因为它想搬走的东西里，有 26 秒只是一个环境变量。

仓库里的实测记录是 `docs/comfyui-measurements.md`，下面每个数都能按节号回去核。

## 第一把刀来自一次插计时

第一天做的事很笨：给 ComfyUI 的四个函数临时插计时，另起一个实例跑，生产那台全程不重启（Python 已经把原文件 import 进去了，改源文件不影响活的进程），探针自带 `cuda.synchronize()`——不然量到的只是提交时间。测完 `git checkout --` 撤干净。

拆开之后跳出来两件意外的事。

第一件：我们传给编码节点的 `negative_prompt` 是空串，节点照样把两张参考图又过一遍视觉塔（31.9 秒）再走一遍 8B（12.5 秒）。负向这一整趟 44.4 秒，占一次 1K 请求的 31%，而 cfg=1.0 时采样器永远不读它。这不是配置能改的——正负两次编码在同一个节点里面，图上怎么接线都改不了。所以只能改代码：从 0.43 的 `nodes_qwen.py` fork 一个节点，删掉三行。

省下来的数：1K 从 150.3 到 101.2 秒。验收方式是最幸运的地方——同 seed 出图逐位相同，差异像素 0.000%，单像素最大差 0。"省 44 秒而图一个像素都没动"这种承诺，只有逐位相同才敢写。

第二件：视觉塔的产出算完就被扔掉。2865 行进、2750 行丢，真正进 DiT 的条件只有 115 个 token。这条当时看着只是个事实，后来变成了那整条 llama.cpp 路线的起点。

AI 替我守住的一条：那个 fork 节点能成立的唯一前提是 cfg 必须等于 1.0。它主动写了"哪天 cfg>1，这里出来的图就不是官方版那回事，是错，不是慢"，并且在测试里把图里那颗 cfg 钉在 1.0。改动带来的风险它不藏，写在节点文件的头注释里。

## 差点走上远路：那个"快 10 倍"

第二天上午的推论是：既然 2750 行算完就丢，那能不能少喂点？能不能换个执行引擎？

在同一颗 APU 上用 llama.cpp 跑同一批 vision token，量到 1.12 毫秒每 token，ComfyUI 是 11.93，差 10.6 倍。而且两边对得上账（grid 96×72 → 合并 1728 token，两边完全一致），所以不是单位或算法数错了。当时的判断写得很硬：那 10 倍是实现差距，不是算法差距，也不是硬件差距。

按这个数，值得开一个大工程：自己编译 llama.cpp、写 C++ 调用程序、做新节点、评图。

真正把这件事拦下来的是它自己补的一句刹车：既然 10 倍是 kernel 差距，ComfyUI 侧也可能有就地修法，先查这个再做移植，工作量差一个量级。

于是先做了 op 级剖析——真权重、真 ops、逐叶子模块计时。结果：

- 一趟编码 46.61 秒里，`Conv3d (patch_embed)` 两次调用共 25.98 秒，55.7%；而视觉塔那 27 层的 Linear 全部加起来才 1.01 秒。
- 那个卷积在数学上就是个矩阵乘：kernel 与 stride 都是 `(2,16,16)`，无重叠。同权重同输入实测，Conv3d 16538 毫秒，GEMM 0.80 毫秒。

中间有两次假信号差点把这条线掐掉：AI 第一版复刻代码多 `permute` 了一次，喂进去是被压扁的破图，于是"随机权重只要 0.38 秒"是假的；另一个坑是 ComfyUI 那些模块的 `reset_parameters()` 返回 None，随机建出来的模型权重是未初始化的垃圾位，也量不出真东西。两次都是靠"换成真权重、真形状"才立住。

最后定死这件事的是一个很便宜的招：同一个卷积，只 `import torch` 时 0.70 毫秒，一旦 `import comfy.model_management` 就变 16538 毫秒。那就不在模型里查了，去读那个模块——`comfy/model_management.py:486-490`，AMD 上除非设了 `COMFYUI_ENABLE_MIOPEN=1`，ComfyUI 会把 `torch.backends.cudnn.enabled = False`，注释写着 "Seems to improve things a lot on AMD"。

一行环境变量。编码段 47.5 秒到 19.5 秒，全量 102.1 到 73.2 秒。四个档位稳态都重测了：480p 11.2、720p 29.1、1K 73.2、2K 302.5 秒。

那 10 倍里有 26 秒是它自缚手脚。llama.cpp 只是不受这个开关影响而已。移植的动机当场从 −36% 掉到 −10%~−15%。

复盘下来我认为值得留下的是这句：这个开关是 ComfyUI 针对 AMD 的默认行为，看起来像"官方替 A 卡调过"，所以一整天没人觉得它奇怪。把它揪出来的不是想到要优化，是先按 op 拆一遍、再决定要不要动手那个次序。

## 数字判不了的那一半

移植看起来死了，但还剩一个更根本的问题：拿不拿得到 llama.cpp 的 pre-norm 出口。因为条件取的是"最后一层 hidden state 且不加最终 RMSNorm"，而 llama.cpp 的默认出口已经过了 norm。这是生死线，比速度先。

判死实验的结果很难看：带图的逐位置余弦只有 0.687。据此判"不做"，理由有三条，其中一条我认为是那三天里最好的一次判断——那个读数连"差在实现还是差在权重"都分不开，在分不开的前提下动手，等于把工程押在没测准的数上。

第二天它把这个数做穿了，结论是自己的数作废：0.687 是行号坐标系用错。`image_spans` 是丢掉 system turn 之前的完整序列坐标，拿去切已经丢过头的张量就整块错 14 行。补上 pre-norm 出口（本地补丁 +15 行，而且 HTTP 那条口拿不到，所以必须自己编译）之后逐位置重测：0.98247。收益也订正成 −19%。

然后就卡在一件数判不了的事上。0.982 是相对 L2 0.196 的条件扰动，而前面只换个卷积实现（扰动小一个量级）都已经有 63% 像素不同。"会不会画出一张看得出不一样的图"，只能生成出来给人看。它当时的结论是"如果只看数字我倾向仍不做"。

注进生产图打了一发，我看了对照图。同构图，脸、姿势、衣服层次都对，差别是抬起那只手的袖口门襟多了一颗金属扣。我说可以接受。这一档才继续往下走，最后拿到 64.5 秒。

"AI 帮不上忙的地方"在这儿有条挺清楚的线：它能把价签写好（0.330% 的像素通道差过 16、PSNR 38.40、构图掩膜质心两腿一致），但"一颗多出来的纽扣值不值 8.7 秒"这个问题没有度量答案。所以这一档现在不是任何人的默认，是我想点就点的一档。

## 两句 export，一个是假的

起因最朴素。我贴了两行想加的启动环境变量：`MIOPEN_FIND_MODE=FAST` 和 `MIOPEN_ENABLE_CACHE=1`。

第二条判死只花一条命令：拿 `strings` 直接问 libMioOpen.so，只有 `MIOPEN_DISABLE_CACHE`，没有 `MIOPEN_ENABLE_CACHE` 这个名字。设了不报错也没效果。这件事的意义不在省了一步，而在它没有去背文档——文档里那种"看起来合理"的变量名，背错了就会一直以为已经处理过。

第一条是真的，但它只管"这台机器没见过的卷积形状"，稳态一分钱不省。那就量一下冷账到底多贵：端到端生产图，新进程加空 db 197.3 秒，同进程第二发 73.2 秒，拆开是调优 116.8 秒、模型载入 7.3 秒。冷 db 那一发贵 124.1 秒，也就是 2.7 倍，而应用的超时线是 300 秒。所以"上线前四档各打一发预热"不是讲究，是别让第一个用户撞超时线。

接着问 FAST 换不换图。这里 AI 交了一份我不能用的卷：那一轮四条腿各带了不同的 prompt 后缀——后缀本来就是它为了计时加的（不加就会整链重放、量不到编码），但加了后缀就是四份不同的条件，于是它们两两之间 49%~60% 的像素差不说明任何事。整轮像素比对作废，重跑成"同一句话跨四种制度"。

订正之后：空 db 从头调优与攒了三天的真 db 出图逐位相同；FAST 会换 VAE 的卷积内核，54.104% 的像素逐位不同，但通道差过 16 的只有 0.70%，PSNR 36.36。看图判：差别在垂着那只手的袖口卷起程度——一边盖到手腕，一边露出前臂。

两条都不设。省的是首发的 124 秒，花的是从此每一张图的逐位复现。这笔交易它把两边都标了价，最后是我的口味。

## AI 交卷时不会自己觉得不对

那三天里我做的最重要的事不是想点子，是把验收口径写死在文档第一节，然后在它每次交一份很像样的卷子时问一句：两边比的是不是同一件事。

举几个当场看着都成立的错。

它一开始报"跨机器约 80% 像素不同"，那是把三通道直方图里第 2、3 通道的零值桶当差值算了——任何两张图都会白送 66.7%。改成每像素三通道取最大差，跨机器其实是 66.56%。

它在推算里给 llama.cpp 那条路估了 −10%，第二天量出来是 −19%，自己作废了前一个数。

它对低两档按机制推了一句"低档反而更慢"，还先把推出来的秒数写进了界面文案。并排量完：1K 快 8.7 秒（这还是下限，那一发仍含新进程载权重）、720p 快 3.7 秒、480p 慢 0.6 秒。所以那句推测错了一大半，但方向在 480p 上是对的——省掉的不只是"编一次"，连那颗 8B 的载入都整个免掉了；只是这一档原本编码就只值 3.9 秒，抵不平桥那 7 秒。

它给第三个来源写文案之后，自己在浏览器里点了一遍页面，又抓到一处：取值回退写成了 `||`，缺一个格子就会念出"实测约 0 秒"。发现是它，写错也是它，两次都发生在东西已经交出来之后。

还有一处是这次写汇总时抓出来的：那份汇总里把第三个来源的收益标成"同实例配对"，实际用的三个基线（11.2 / 29.1 / 73.2）来自另外两次单独的测量会话。这正是实测记录第 25.4 节里它自己刚写下的一句——"跨节拿绝对值相减不可信"。警告和犯它之间隔了不到一天。

这三天沉淀下来的口径只有一条我觉得最值钱，也是这么来的：判"改了 X 会不会换图"，先核对两边的输入字节。同一个文件走不走一遍上传前的 JPEG 重编码，人像会有平均 0.94/255 的差，最大到 18；光是这一点就够让成图有 0.098% 的像素通道差过 16，而第三个来源那一改总共才 0.330%。差值是三分之一的量级，就足够把账记到错的那一处头上。

共同点很一致：每一次都是"能跑完、数也合理"。它不会在交卷时觉得不对。所以口径要在动手之前写死，而不是在出事之后补。

## 数不能跨机器搬

同一处改动在两台机器上差着量级。

| 改动 | 本机 8060S | RTX 5060 Ti 16GB |
|---|---|---|
| 少编一遍负向 | −44 秒 | ≲1 秒（四对独立比较都是这个量级） |
| 加 `--use-ck-attention` | −1 秒 | −10.7 秒（−28%） |
| 编码段本身 | 89.4 秒 | 9.0 秒 |

差距几乎全在编码那一段，因为那颗 8B 是纯带宽活儿。所以本机这一路的收益，换一台机器就要重打一遍判据，不能把"省 44 秒"当承诺搬过去。这也是为什么那几张跨机器倍数表被改了三次（2.7×→3.1×、5.5×→9.5×、1.5×→2.1×）——每一次都是新变量，不是硬件变了。

## 最后

三天里真正的大刀只有两把，都砍在编码上：一把是把没人读的负向那一趟删掉（−44 秒，出图逐位相同），一把是打开被关掉的 MIOpen（−28 秒，出图换了）。第三把（llama.cpp 编码，1K 64.5 秒）不是砍，是一笔用复现能力换时间的交易，我把它做成了一档可选项而不是默认。

而 attention 后端那一整轮——四种后端、两台机器、十几发 GPU 时间、一份 flash-attn 的装法备案——本机净收益 1 秒。按投入产出它是最失败的一段；按它换来的两句判据（换后端会换图，所以逐位相同不能跨后端当验收；收益跟机器绑定，所以判据不能搬），后面每一步都在用。

还剩一刀没砍：让视觉塔少看点像素。数上预期全量还能再减 16% 到 23%，但它是纯粹拿画质换时间，而且必须先解决一件事——我们到今天还不知道那 0.982 的残差是差在实现还是差在权重（要用同一份权重转一个 gguf 才能分开）。归因没分开之前不动它。
